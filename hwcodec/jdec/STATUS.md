## Honest verdict

- The **11 [V] words are done**. A kernel driver can build the whole 2015-register frame-mode sequence today.
- The **9 [I] slots and 4 index pointers are hypotheses**, each with candidates and an experiment. The two most likely
  surprises are: (a) the hybrid needs a huffman/tile index (0x338/0x36C/0x370/0x374) fed by software, not just zeroed
  memory; (b) 0x330/0x334 are the strides (the hybrid word list has no other stride) and 0x31C is a table/BRZ/BRP word.
- **Feasibility in experiment counts**: if E2 works, hardware decode needs **1 decoder write experiment** (plus the E1
  read-only power/defaults pass) and no vendor library. If E2 fails but E3 works, **2 write experiments**. If both fail,
  each remaining hypothesis is one E4 run (about **12 write cycles**), or **0 phone experiments** if the host capture of
  the vendor library succeeds first.
- **Do not bet the milestone on E2.** The hybrid is a different IP revision with index/progress registers that the open
  driver never uses; a plain frame-mode decode may well fail. The reliable shortest path is the host capture (option 1 of
  `PHONE_EXPERIMENTS.md`): run the phone's own 32-bit `libjpeg-alpha_vendor.so` + `libjpeg-alpha-oal_vendor.so` under the
  A32 interpreter with a fake OAL `syscall`, capture the exact 21-word task for a known JPEG, then compare it with our
  generated words. That is a track V/IV task and is **not done here**. **Without the vendor library, hardware decode is
  not proven feasible from the open sources alone**; with it, it is.

## Not done / unresolved

1. No phone run of anything; E0-E6 are written but not executed.
2. No host capture of the vendor library; the exact word values for a real JPEG are unknown. Proposed to `hw-iv`/`hw-lead`,
   not implemented.
3. The 9 [I] words and 4 index pointers remain hypotheses; `REGISTERS.md` lists the candidates and E4 the distinguishing runs.
4. The index buffer's 3-table layout is an inference; the vendor's `data[20]` allocation is only one table wide as written.
   Our kernel must allocate 3×size until E1/E5 or the host capture says otherwise.
5. `data[12]` is the aligned **buffer** size rather than the file length: the vendor's `[HYBRID] jpeg_hy_set_src buffer size is
   not alignment` string supports that, and our `align(file bytes,128)` is the minimum valid value. Still [I] for a larger
   vendor allocation (R2 F31).
6. No kernel/user integration: K01's `RWJ_DECODE` still answers ENOTSUP; the parser/words are offered as the shared
   implementation but not wired in.
7. Parser limits by design: baseline SOF0 only, 8-bit, one interleaved scan, 1 or 3 components, no abbreviated streams, no
   DNL, no arithmetic/progressive. 4:2:2X2 (H0=4) is parsed but refused for word generation because the open `mcu_w`
   formula gives a 64-pixel MCU while T.81 gives 32.
8. Review: R2 accepted the package with F30 (the [I] words / hardware decode not proven) and F31 (`data[12]` and the
   3-table index allocation are inferences), both marked "open (documented)" in `review/r2/FINDINGS.md`. My answer is on the
   board (J04 -> R2, message 1794411141543645316): no code change is possible without the vendor capture or the phone;
   `data[12]` gained direct evidence from the vendor's `jpeg_hy_set_src buffer size is not alignment` string (aligned
   buffer size, not necessarily the file length). F30 stays open until the host capture or E2/E3.
9. No 12-bit/4-component/2-component hardware claim; no entropy decoder (not needed: the block decodes the entropy itself).

## Known risks

- A wrong 0x330/0x334 (stride vs dimension) gives an overflow or silently corrupt picture; E4b/E4c distinguish.
- Writing 0x31C with a bad address could make the block DMA from/to nowhere; the E4e/E4f trials use a zeroed 4 KiB table
  inside the claim.
- The three cores share larb7's clocks; core 2 needs larb8 and the venc_c1 gate, which no 0298 code has touched. E6 is last
  for that reason.
- The decoder's 0x274 is not cleared by the hybrid start; a stale EOF can be mistaken for completion. Our experiment
  clears it explicitly.
