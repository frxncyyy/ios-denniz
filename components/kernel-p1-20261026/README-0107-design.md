# 0107 design: CPU DVFS bring-up under XNU on the MT6893 (host-only analysis of the stock Android kernel)

Status: analysis and design only. Nothing here has run on a device. The only code that came out of it is a READ-ONLY probe (patch 0109, image `probe350mcu`, needs separate approval to run).
Numbering note: "0107" is this document; the patch numbers 0108/0109 are the WAIT_SEQ fix and the probe (see the end).

## 1. Method
Input: `research/nord2/stock-Image` = the Android kernel this phone boots, Linux 4.19.325 (a NetHunter build of the vendor tree; strings, symbols and code are the vendor's MediaTek DVFS code). Private working material, not to be published.
Tools (host, scratch only): `vmlinux-to-elf`/kallsyms extraction (156 044 symbols, text base `ffffff8008080000`), capstone AArch64 disassembly with ADRP/ADD string and symbol resolution. Every address below is a kallsyms address of that image.
Public guide: upstream `mediatek-cpufreq-hw` bindings (domain windows `0x11bc10` and `+0x90` per domain in the first versions, `+0x120` in later ones) and the MediaTek vendor `sspm-cpufreq.c` (4.19): "write the OPP index to `csram + 0x37c + 4*cluster`".

## 2. What owns CPU frequency on this SoC
**The MCUPM co-processor (MCU power manager, DT `mediatek,mcupm` at `0x10300000`), not the SSPM and not the AP.** The Android kernel is only its client:
1. It copies a static OPP table into the cpuhvfs CSRAM (`0x0011bc00`, 0x1400 bytes).
2. It sends MCUPM a few IPI messages (init table, segment, initial voltages).
3. Afterwards a frequency change is one 32-bit store of an OPP index into the CSRAM; MCUPM does PLL and voltage.
The kernel never loads MCUPM firmware (no loader symbol: `mcupm_device_probe`, `mcupm_reserve_memory_init`, `mcupm_plt_init`, `mcupm_alive_show` only); the bootloader does, as on the reference SoCs. Whether it does so on this boot chain is **unknown** (section 7).

### 2.1 Android init sequence (initcall order)
| level | function (address) | what it does |
|---|---|---|
| 3 | `mcupm_init` (`ffffff800a4a04a4`) | registers the MCUPM platform driver, reserves the 2 MiB `mcupm_share` memory |
| 5 | `cpuhvfs_pre_module_init` (`ffffff800a4a0de4`) | `dvfsp_module_init` (maps the `mediatek,mt6885-dvfsp` reg = CSRAM `0x11bc00`/0x1400 into a global pointer), `mtk_ipi_register(&mcupm_ipidev, 1, ...)` (cpufreq IPI id 1), `cpuhvfs_pvt_tbl_create`, then IPI **cmd 0** `{0, 0}` ("init table") |
| 6 | `mcupm_module_init` | sysfs, platform IPI |
| 7 | `_mt_cpufreq_pdrv_init` -> `_mt_cpufreq_pdrv_probe` | `cpuhvfs_set_init_volt` (IPI **cmd 10**, once per cluster, 4x) then `cpuhvfs_set_init_sta` (IPI **cmd 1** `{1, cpu_level}`), then `cpuhvfs_module_init` (debugfs, thread `ipi_cpu_dvfs_rtask`); per cluster `_mt_cpufreq_init` -> `cpuhvfs_set_cluster_on_off` |
| run time | `_mt_cpufreq_set` etc. | `cpuhvfs_set_dvfs` = index store; `cpuhvfs_set_min_max` (limits); `cpuhvfs_set_freq` (IPI cmd 4 `{4, cluster, freq}` for the debug path) |

### 2.2 CSRAM map (offsets from `0x11bc00`)
| offset | content | written by |
|---|---|---|
| `0x10..0x250` | the OPP tables, four domains at a **0x90 stride**: LL `0x10`, L `0xa0`, B `0x130`, CCI `0x1c0`; each domain = array A (16 words: `freq_MHz` in bits [11:0] plus `volt` in bits [27:16]) at +0x00 and array B (16 words: `divider` in bits [7:0], second field in [23:16]) at +0x40 | AP (`cpuhvfs_pvt_tbl_create`, `ioremap(0x11bc10, 0x240)`) |
| `0x2a4/0x2a8` | turbo scale words | AP (`cpuhvfs_set_turbo_scale`) |
| `0x2b8/0x2bc/0x2c0` | turbo disable, sched-DVFS disable, DVFS stress | AP |
| `0x320 + 4*c` | per cluster `min_idx \| max_idx << 16` | AP (`cpuhvfs_set_min_max`) |
| `0x32c + 4*...` | current voltage readback | MCUPM |
| `0x354 + 4*c` | **current OPP index readback** | MCUPM (`cpuhvfs_get_cur_dvfs_freq_idx`) |
| `0x37c + 4*c` | **OPP index request** (c = 0 LL, 1 L, 2 B, 3 CCI) | AP (`cpuhvfs_set_dvfs`) |
| `0x1218 + 4*c` | "advise freq" on/off magic | AP |
| `0x1224 + 4*c` | cluster on/off magic (`0x43434f46`, `\|8` = on) | AP (`cpuhvfs_set_cluster_on_off`) |
This is **not** the generic `mediatek-cpufreq-hw` register block (`ENABLE +0x84 / PERF_STATE +0x88 / HW_STATE +0x8c` are absent: the request word is at `0x37c`), which is why a 0104-style PERF_STATE writer could not have worked even with a running engine. The LUT row format (freq in [11:0], volt above) is the same idea, at a 0x90 domain stride instead of 0x120.

### 2.3 The IPI transport (MediaTek tinysys mailbox)
`mtk_ipi_send_compl(&mcupm_ipidev, id, wait=1, msg, len_words, timeout_ms)` (`ffffff8008637df8`); every cpu-dvfs message is `id = 1`, `len = 4` words `{cmd, a1, a2, a3}`, timeout 2000 ms (cmd 7: 4000 ms). Underneath (`mtk_mbox_write_hd` `...86352f4`, `mtk_mbox_trigger_irq` `...86357e8`): the message is stored (16-byte header, then payload) into the mailbox slot memory, then the pin bit is written to the mailbox "set IRQ" register; completion is an acknowledgement read back through the recv side (`mtk_mbox_polling` or the interrupt). The pin table (`mcupm_mbox_pin_send`, 0x60-byte entries) gives message sizes 3/4/9/3/3 words for ids 0..4 (id 1, cpufreq = 4 words, which matches the 4-word send) and the entry fields that equal n suggest mailbox n for IPI id n (inference, not confirmed).
From the live DT (`mcupm@10300000`): firmware SRAM `0x10301000` (0xb800), mailbox slot memory `mbox0..4` = `0x1031fce0 + 0xa0*n` (0xa0 bytes each), and the four control registers shared by all mailboxes: `0x10300074` (clr), `0x10300078` (recv), `0x10300150` (send), `0x10300154` (set); IRQs SPI 178..182. Liveness check used by the Android kernel (`mcupm_alive_show`): IPI id 0 with `{0xdead}`, "Alive" if the callback fired.
**Decoded since (section 11.2)**: slot offsets, message sizes and the acknowledgement format of every pin, from the stock Image's static tables and the vendor source tree on disk (`work/nord2-current-kernel`).

## 3. The OPP table of THIS chip (and why it matters for safety)
`_mt_cpufreq_get_cpu_level` (`ffffff800888cb58`): `devinfo[7] & 0xff == 0x10 -> level 0; == 0x40 -> level 1; else (devinfo[0x84] >> 13) & 1`. This phone's devinfo word 7 (the `atag,devinfo` of `dtb/nord2/live.dts`, cell 8, byte-swapped as stored) has low byte **0x40 -> level 1 -> table `FY_30G26G`** (big 3.0 GHz, little-big 2.6 GHz, matching the DT `clock-frequency`s). Level selects `xrecordTbl[level]` (`ffffff800a715c58`; tables `FY_26G26G`, `FY_30G26G`, `FY_30G28G`); `update_pvt_tbl_by_doe` only overrides from DT `doe_dvfs_cl*` nodes, which are empty on this phone, so the static table is what the kernel uses. Rows are `{MHz, volt in 6.25 mV units, divider, 1}`:
* LL (cpu0-3): 2000/1000 mV, 1800/950, 1725/931, 1625/906, 1525/881, 1450/862, 1350/838, 1250/812, 1075/769, 1000/750, 925/731, 850/712, 750/688, 675/669, 600/650, 500/650
* L (cpu4-6): 2600/1050, 2507/1031, 2354/1000, 2200/969, 1985/919, 1855/894, 1740/869, 1624/844, 1537/831, 1451/812, 1335/788, 1162/750, 1046/725, 902/694, 700/650, 700/650
* B (cpu7): 3000/1050, 2892/1031, 2713/1000, 2600/981, 2463/956, 2284/925, 2141/900, 1998/875, 1820/844, 1632/812, 1482/788, 1370/769, 1258/750, 1108/725, 921/694, 659/650
* CCI: 1700/1000 ... 520/650
What the device logs show against it: LL measures ~1791 MHz = row 1 (1800 MHz, 950 mV): the bootloader leaves LL at that row. L and B measure ~730 MHz, which is in no row of either table: 728 MHz = 26 MHz x 28, a bootloader PLL setting at a voltage we cannot read. So "stuck at the bootloader's setting because nobody ever requested a frequency" is now an established reading, and the CSRAM being power-up noise (README-0106) says the MCUPM never received the tables.
**Safety consequence:** the voltages MCUPM would apply are the static, conservative table values (650-1050 mV, no EEM/AVS undervolt). Nothing in this design lowers a voltage below what the stock kernel's table specifies for this chip level, and the AP never writes a rail or a PLL.

## 4. What the data proves and does not
Proves: the CPU clocks are the bootloader's; the DVFS tables and init were never delivered; the mechanism and the protocol above; the chip's OPP table and level.
Does not prove: that the MCUPM firmware is running; what it does with `{0,0}`, `{1,level}` and `{10,c,vA,vB}` internally; what its power-on OPP choice is after init; the mailbox slot/ack format; the meaning of `vA/vB` units (uV or regulator selectors) and of the second field in array B.

## 5. Unknowns that block any write (each has a way to resolve)
1. MCUPM alive? -> the read-only probe (section 9): control registers, mailbox slots, SRAM head.
2. Mailbox slot offsets and ack format -> finish decoding `mcupm_mbox_pin_send/recv` and `mtk_ipi_send_compl`/`mtk_mbox_polling` (host, no approval needed).
3. `cmd 10` payload: units and source of `vA/vB` -> decode `cpuhvfs_set_init_volt` fully (`id_to_buck_ctrl`, `buck_ctrl` at `ffffff800a7169b8`, regulator ops) and the PMIC register behind it (MT6315/MT6359 vproc, `mt6315_vproc_transfer2volt`); the same values are what the bootloader left in the PMIC, i.e. readable.
4. Post-init default OPP of MCUPM -> not knowable offline. Mitigation in the design: bound the range first (`min/max` words) and make every step measured.
5. Array B second field and CCI handling -> decode `cpuhvfs_pvt_tbl_create` stores; copy the table bytes verbatim from the image instead of re-deriving them.

## 6. Safety story (required by the approval)
* **Voltage owned by firmware**: MCUPM sets Vproc/Vsram from the verbatim stock table. The AP passes only what the stock kernel passes (init voltages read back from the PMIC) and never writes a rail, a PLL or an EEM/AVS register.
* **Verify by measurement, restore on mismatch**: the 0099 CPU-clock oracle (dependent-add chain vs the generic timer) after every requested index; accept only within 8 % of the table row; otherwise write the previous index back and freeze the cluster for the boot. Readback `0x354+4*c` is logged next to the measurement and must agree with the request.
* **Bounded range before any request**: `min/max` words (`0x320+4*c`) set to the bootloader's row (min = max = nearest row) before the first request, then widened one row at a time. LL and CCI are never requested (LL stays at the bootloader's row); only L and B move, to a cap of 2.0 GHz by default (L index of 1985 MHz = 4, B index of 1998 MHz = 7).
* **Temperature**: battery-gauge guard as in 0104 (no start at >= 40.0 C, one row slower per 2 s tick at >= 43.0 C, one faster again below 38.0 C, never above the cap or below the bootloader row), plus the MCUPM's own thermal limiting if it is on. No SoC sensor exists (LVTS not running); the weak input is stated, which is why the default cap is 2.0 GHz and not 2.6/3.0.
* **Irreversibility**: the init IPIs cannot be undone (no "deinit" command was found). The fall-back after a failure is "pin min = max = the bootloader's row for every cluster and stop sending requests", not "restore the pre-init state". This is why stage 2 is gated on the probe and on a ping.
* **No blind steps**: every stage below has a stop condition and logs raw words; the first write-capable stage sends only the harmless liveness ping.

## 7. Is the MCUPM running? (the gating question; answered in part in section 11)
On the reference SoCs the bootloader starts it; the Android 4.19 kernel here has no loader, so the same is expected, but the CSRAM being uninitialised only says nobody sent the init, not that the firmware is absent. Evidence to collect (read-only): mailbox control registers (sane values vs all-ones/zero), mailbox slot memory (a running firmware leaves headers/magic in its recv slots), the SRAM head (firmware image/stack vs zeros or power-up noise exactly like the CSRAM). A running MCUPM also leaves `mcupm_share` log buffers in DRAM (address not known to us: the reserved region is allocated by the bootloader).

## 8. Bring-up plan (every stage gated, each its own device boot and approval)
0. **Host only, now**: decode the remaining unknowns of section 5 (mailbox slots/ack, init-volt payload), write the port as pure code with a model of CSRAM + MCUPM (accepts exactly the Android message sequence; rejects anything else) and a replay test that the AP's complete write set equals the stock kernel's.
1. **Read-only probe** (`probe350mcu`): section 9.
2. **Ping** (only if stage 1 shows a plausible live MCUPM): send IPI id 0 `{0xdead}` and wait for the acknowledgement; no table, no CSRAM write.
3. **Tables + init**: copy the verbatim level-1 table into CSRAM `0x10..0x250`, write `min/max`, send cmd 0, cmd 10 (x4, initial voltages), cmd 1 (level 1), cluster-on magic; read back `0x354+4*c`. No frequency request yet; measure that nothing moved (CPUCLK unchanged) - if MCUPM moved a cluster on init, that is the first thing the log must show.
4. **First request**: one L step by one row, measured; then the 0104 controller (verify/restore, guard) with the CSRAM-index driver instead of PERF_STATE.
5. Governor (0106 decision logic) only after 4 is boringly stable.
Effort estimate: stage 0 about two days of host work plus decoding; stages 1-4 each need a device boot.

## 9. The read-only artifact (needs separate user approval)
Image `gpu/build/device-mmu-p12-candidate/probe350mcu/nord2-ios-metal-p12-probe350mcu-stop23.img`, sha256 `f518a4f5e0b942b8320d40521e1d70ba1be6e31c0ff8dba37cdb4421c470ceab`, kernel stage `device-mmu-p12-candidate/kernela` (0085-0098 + 0100-0106 + 0108 + 0109), command line 593 characters = the probe base plus `n2mcu=1` (no GPU load: `nord2_metal=0`, 350 MHz).
At boot + 60 s a kernel thread prints, with plain 32-bit loads only (the source of `n2mcu_probe` in `nord2_cpufreq.c` contains no store to any mapped address; map = `ml_io_map` of three 4 KiB device pages):
* `NORD2 MCUPM reg 0x10300074/78/150/154` (clr/recv/send/set),
* `NORD2 MCUPM mbox0..4 +0xNN` : 0xa0 bytes each of the five mailboxes at `0x1031fce0 + 0xa0*n`,
* `NORD2 MCUPM sram +0xNNN`: the first 256 bytes of `0x10301000`.
Nothing is sent, no interrupt is enabled, no CSRAM write. Expected readings and what they mean: (a) SRAM head all-zero/ones or power-up-noise statistics as in README-0106 -> firmware absent, stop; (b) a recognisable image header/strings or small structured values, mailbox slots with non-noise words -> alive, stage 2 becomes meaningful; (c) all-ones everywhere -> the block is unpowered/unclocked (reads are harmless in that case only if the bus does not stall).
**Risk to state for the approval**: a block whose clock or power domain is off can stall the AXI/APB read; this kernel has no abort recovery, so the phone would hang until the watchdog/reset. The MCUPM control block sits next to blocks the Android kernel reads freely after boot, and the probe runs 60 s after boot, so the risk is judged low but not zero. It is the reason this is a separate image with its own boot-arg and not part of any UI image.

## 11. Result of the read-only probe `probe350mcu` (ran on the device, no hang) and what it means
Log: `gpu/build/hardware-20261025/c6p-test/mcu-usb/xnu-live.log` (grep for `NORD2 MCUPM`). Sources used for the interpretation: the stock Image (kallsyms and disassembly) and the vendor 4.19 tree on disk, `work/nord2-current-kernel/` (`drivers/misc/mediatek/mcupm/`, `drivers/soc/mediatek/mtk-mbox.c`, `drivers/misc/mediatek/lpm/modules/{include,platform}/mt6885`, `arch/arm64/boot/dts/mediatek/mt6893.dts`). I had not used that tree before section 2; it agrees with the disassembly and removes the "Not decoded yet" item of section 2.3.

### 11.1 Observations
| item | reading |
| --- | --- |
| control registers `0x10300074/78/150/154` (clr, recv status, send status, set) | all 0: no pending doorbell in either direction; the block is clocked and answers reads |
| mbox0, mbox1, mbox2 (whole 0xa0 bytes each) | high-entropy noise, never written (same statistics as the CSRAM in README-0106) |
| mbox3 `+0x00..+0x4f` | 20 words deliberately written: all 0 except `+0x20 = 1`; `+0x50..+0x9f` noise |
| mbox4 | zeros at `+0x24` (slot 9) and `+0x30..+0x3f` (slots 12..15), noise elsewhere |
| SRAM `0x10301000..+0xff` | all zero (not noise, and not a vector table) |

### 11.2 Decoded protocol (stock tables `mcupm_mbox_table` ...a70b130, `mcupm_mbox_pin_send` ...a70b310, `mcupm_mbox_pin_recv` ...a70b4f0, and vendor `mcupm_ipi_table.h`)
Mailbox n (n = 0..4) is the 0xa0-byte memory at `0x1031fce0 + 0xa0*n`. It is split into a send half (AP to MCUPM, slots 0..19 = bytes 0x00..0x4f) and a receive half (MCUPM to AP, from slot 0x14 = byte 0x50). One IPI channel = one mailbox, pin_index = n, and the four control registers are shared: bit n of every register belongs to mailbox n. The AP rings the doorbell with `writel(1 << n, 0x10300154)`; MCUPM answers by writing its reply into the receive half and raising bit n of `0x10300078`, which the AP clears by writing the bit to `0x10300074`; `0x10300150` is the "send still pending" status (`mtk_mbox_trigger_irq`, `mtk_mbox_polling`, `mtk_mbox_check_send_irq` in mtk-mbox.c; field layout of the pin words from `mtk_mbox_print_send/recv` in the Image: bits 3:0 mbox, 23:4 slot offset, 25:24 send option).
| IPI id | user | mailbox | send message (words) | reply (words) |
| --- | --- | --- | --- | --- |
| 0 CH_S_PLATFORM | plt init `{0x504C5401, phys, size}`, alive check `{0xdead}` | 0 at 0x1031fce0 | 4 (stock alive check sends 3) at +0x00 | 1 at 0x1031fd30 |
| 1 CH_S_CPU_DVFS | the CPUHVFS commands of section 2 | 1 at 0x1031fd80 | 4 at +0x00 | 4 at 0x1031fdd0 |
| 2 CH_S_FHCTL | frequency hopping | 2 at 0x1031fe20 | 9 | 1 |
| 3 CH_S_MCDI | CPU idle | 3 at 0x1031fec0 | 3 | 1 |
| 4 CH_S_SUSPEND | suspend | 4 at 0x1031ff60 | 3 | 1 |

So "which mailbox slot does the CPUHVFS IPI use": mailbox 1, words 0..3 at 0x1031fd80, doorbell bit 1 of 0x10300154, reply of 4 words at 0x1031fdd0 flagged by bit 1 of 0x10300078. Mailbox 3 is not an IPI mailbox in practice: it is the AP/MCUPM shared control block of the low-power driver.

### 11.3 Is `mbox3 +0x20 = 1` a firmware flag? Yes, and a specific one
Vendor header `mtk_lp_plat_apmcu_mbox.h` (mt6885, same family): `APMCU_MCUPM_MBOX_ID = 3`; slots 0 AP_READY, 4 PWR_CTRL_EN, 5 L3_CACHE_MODE, 6 BUCK_MODE, 7 ARMPLL_MODE and 12 WAKEUP_CPU are written by the AP (default 0). Slot 8 TASK_STA is read-only for the AP: 0 UNINIT, 1 INIT, 2 INIT_FINISH, 3 WAIT, 4 RUN, 5 PAUSE. The stock Image does exactly this at boot (`mtk_wait_mbox_init_done`, ffffff8008be5320): `mcupm_mbox_read(3, 8)` once a second until it reads 1 (INIT); then it writes slot 7 = 2, slot 6 = 2, slot 4 = 0xf (MCUSYS|BUCK|ARMPLL|CM power control), and `mtk_notify_subsys_ap_ready` later writes slot 0 = 1. The probe read TASK_STA = 1 with slots 0..19 otherwise zero: the firmware's "early init done, waiting for the AP" state with every AP-owned slot still at its default. Noise cannot produce 20 consecutive zero words plus a single 1 at the one documented status slot (probability around 2^-640), and nothing in this boot (XNU, no Linux) has written there from the AP side.
Mailbox 4 has the same character: slots 12..15 (`+0x30..+0x3f`) are the time-sync block of `mcupm_timesync.h` (TICK_H/L, TS_H/L) and slot 9 is adjacent; five zero words at exactly those positions are not chance, while slots 10/11 (PDN/STATE) and 16/17 are noise.

### 11.4 Is the firmware present and running?
* Present and past its early init: yes. Something that knows the MCUPM mailbox map wrote TASK_STA = INIT and zeroed the shared slots; only the MCUPM firmware (or its loader stub) does that, no Linux ran in this boot, and the value is exactly the exit condition of the stock wait loop.
* Currently executing and servicing doorbells: not proven. All four control registers read 0 (nothing pending), mailboxes 0..2 are untouched, and a halted core would look identical. The state may also be a leftover: SRAM contents survive a warm reboot (README-0106: the CSRAM "noise" repeats across boots), so INIT could persist from an earlier boot in which the bootloader started the firmware. It cannot be a leftover of an Android session that configured the firmware: TASK_STA would then read 3 or 4 and AP_READY / PWR_CTRL_EN would be non-zero.
* The zeroed SRAM head (256 bytes at 0x10301000) is not evidence of an absent firmware. It is a cleared region (power-up noise is high-entropy, README-0106), not a vector table. This platform has `MCUPM_ACCESS_DRAM_SUPPORT = 0`, so the firmware cannot live in DRAM and its code is in the SRAM, just not in the first 256 bytes of that window: a header, a reserved page or another load offset is possible. The window is 47 KiB and the probe read 0.5 % of it.
* Safety meaning of the AP-side defaults: with PWR_CTRL_EN = 0 and AP_READY = 0 the firmware has not been told to manage MCUSYS, the buck or the ARMPLL, and the CPUs run on the bootloader's settings (LL 1.8 GHz, big ~0.73 GHz, consistent with README-0106). A misbehaving ping therefore cannot change a CPU rail or PLL by itself; at worst the firmware crashes until the next boot (the bootloader reloads it every boot).

### 11.5 Consequences for the DVFS plan (sections 5 and 8)
* Unknown 2 (slot offsets and acknowledgement format) is resolved by 11.2. Unknown 1 (alive) is now "present, early init done, running unproven".
* (Superseded by 12.4: the mailbox-3 handshake belongs to the cpuidle initialisation, not to DVFS.) The stock bring-up order is: wait for TASK_STA == 1 (satisfied) -> write mbox3 slots 7, 6, 4 -> AP_READY -> platform IPI PLT_INIT, which carries the physical address and size of the 2 MiB `mcupm_share` DRAM region (section 11.7: allocated by the kernel, so our choice) -> DVFS IPIs. A DVFS IPI before the platform init is unspecified and this design must not send one. The platform init is therefore on the critical path of any stage 3.

### 11.6 Next safe step: patch 0114, the read-only probe `n2mcu=2` / `n2mcu=3` (built, not run; needs its own approval)
Same mechanism and rules as 0109 (32-bit loads only, `ml_io_map`, no store to any mapped address, no interrupt, nothing sent; kernel thread at boot + 60 s). Source: `0114-mcupm-readonly-probe2-n2mcu2.patch` (`bsd/dev/nord2_cpufreq.c` + the new pure header `bsd/dev/nord2_mcupm_scan.h`, host test `tests-new/nord2_mcupm_scan_test.c`, which classifies the real probe-1 mailbox words correctly). What it prints (all lines start with `NORD2 MCUPM`):
1. Everything of n2mcu=1 (control registers, the five mailboxes, the SRAM head), then the whole firmware SRAM window 0x10301000..0x1030c800 (47 KiB, the DT's 0xb800) as a block map: 256-byte blocks classified ZERO / NOISE (ones within 5 sigma of half the bits and no repeated word) / STRUCT, runs of ZERO and NOISE collapsed into one line each, every STRUCT block with its counts, its first eight words and up to two printable strings of six or more characters. Expected log size well under 100 KB.
2. A time series: ten samples 100 ms apart of the four control registers, mailbox 3 slot 8 (TASK_STA) and mailbox 4 slots 9..17.
3. A pointer search (see 11.7) over the window, the gap and the mailboxes.
4. `n2mcu=3` only: the gap 0x1030c800..0x1031fce0 (77 KiB between the window and the mailboxes) as the same map. The Android kernel never maps this range, so it is the only part with an unknown bus answer; it is read LAST in the first pass, after everything else was printed, so a stall costs only the gap data and the liveness pass.
5. At boot + 180 s everything is read again and compared with the first read: changed-word counts, the first 64 changed offsets with old and new values, for the mailboxes, the window and (n=3) the gap, plus changed control registers. A running firmware changes at least counters, stack or timestamp slots; a static result means halted or fully idle (inconclusive, not a disproof).
Images (P16 kernel A, series 0085..0114): `probe350mcu2` (`n2mcu=2`: window, mailboxes, time series, pointers, liveness) and `probe350mcu3` (`n2mcu=3`: plus the gap). The recommended first run is `probe350mcu2`; `probe350mcu3` only after that came back clean.
Risk statement for the approval: the same class as the probe that already ran. The window pages 0x10302000..0x1030c000 are new reads but sit in the SRAM that the stock kernel maps through `mcupm_base` (the first page answered normally); the gap is not mapped by stock and is separately gated. A stall would show as a hang until the watchdog (no abort recovery); there is no store of any kind.
**Stage 2 (a ping, which writes) only if the probe shows activity or a recognisable image.** Content: the stock alive check and nothing else. Write `{0xdead, 0, 0}` to mailbox 0 slots 0..2 (0x1031fce0), ring bit 0 of 0x10300154, poll bit 0 of 0x10300078 for at most 20 ms, read 1 word at 0x1031fd30, clear bit 0 via 0x10300074; never enable SPI 178..182, never write the CSRAM, no mbox3 writes. Residual unknown: whether the platform handler accepts a 0xdead before PLT_INIT (stock never does that). The consequence of a bad reaction is a dead MCUPM until the next boot with the CPUs unaffected (11.4). If the probe shows a static, activity-free window a ping would only time out and is not worth a boot. No ping without separate approval.

### 11.7 Where is `mcupm_share`? (read-only search; corrects section 11.5)
* The live FDT (`dtb/nord2/live.dts`, captured from the bootloader) has `reserve-memory-mcupm_share` with `size 0x200000`, `alignment 0x10000`, `alloc-ranges 0x40000000 + 0x60000000` and NO `reg`: it is a dynamic reservation that the Linux kernel allocates itself at boot (`of_reserved_mem`), not an address the bootloader hands over. The `mcupm_share` base is therefore OURS to choose (any 2 MiB DRAM range that XNU does not use and the firmware may access); nothing has to be found. The platform init message is `{0x504C5401, phys, size}` with that physical address. Correction to 11.5: the "address chosen by the bootloader" remark referred to a different node.
* The bootloader does reserve a fixed 1 MiB `mblock-13-MCUPM-reserved` at 0x7e900000 (`no-map`, compatible `mediatek,MCUPM-reserved`). Most likely home of the firmware image or its working memory before it runs from SRAM. It is plain DRAM, but `no-map` regions are commonly EMI-MPU protected, and an access violation may be a bus error without recovery here, so reading it is NOT part of 0114. If the SRAM map shows pointers into it (below) a separate, separately approved DRAM probe becomes worth considering.
* The probe therefore searches the SRAM window, the gap (n=3) and the five mailboxes for words that point into 0x7e900000..0x7ea00000 (strict) or are page-aligned DRAM bank 0 addresses 0x40000000..0xc0000000 (loose, expect a few noise false positives per 100 KB). A hit near a STRUCT block would be a pointer left by the bootloader or the firmware.

### 12.2 Interpretation
* **The SRAM was actively written during this boot, and that is the strongest new fact.** Compare the two probe boots word by word: the noise-like cells (mailboxes 0..2, the receive halves of mailboxes 3 and 4) differ by 66..127 of 1280 bits per mailbox (about 5-10 %), i.e. the SRAM keeps most of its contents across a reset but decays. A region that was merely retained would decay the same way; the zero regions did not decay at all (mailbox 3's 20 zero words are identical in both boots, and the entire window is exactly zero or small integers, not one noise block in 47 KiB). Something wrote those zeros and values in the current boot, after the decay: either the bootloader clearing the firmware's RAM before releasing the MCU, or the firmware zeroing its own `.bss` and initialising its structures. Together with `TASK_STA = INIT` the second is the natural reading: **the firmware ran this boot**. (A bootloader that cleared the window but knew nothing about mailbox 3 would not leave INIT in the one documented status slot.)
* **Currently servicing doorbells: still not shown.** Zero changes in 120 s, no register activity, no counter that ticks. A firmware that sits in WFI waiting for the AP (state INIT, no timers visible to the AP) looks exactly like this; so does a halted core. Active evidence is the only way to tell them apart: the ping.
* **The window is the firmware's RAM, not its code.** 33 KiB of zeros followed by seven 2 KiB records of counters and flags is the shape of `.bss` plus per-instance data (seven identical records; the eighth would start at +0xb800, exactly where the DT window ends: the window is probably the first 7 of 8 per-CPU records of a 2 KiB structure, which would be the MCDI/idle bookkeeping; this is a guess).
* **No pointer into `mblock-13-MCUPM-reserved` (0x7e900000) and no DRAM pointer** was left in the window or the mailboxes, so nothing in the AP-visible SRAM names the DRAM block or a shared buffer. That is consistent with `MCUPM_ACCESS_DRAM_SUPPORT = 0`: the firmware needs no DRAM address until the AP sends one (PLT_INIT).

### 12.3 Where is the code?
Not in the 47 KiB window: it holds no instruction-like block, no strings and no vector table. Candidates, most likely first, and what would tell them apart:
1. **The 78 KiB gap 0x1030c800..0x1031fce0** (AP-visible SRAM between the window and the mailboxes; the largest unread part, room for a typical tinysys image). `probe350mcu3` reads it (stall risk: the Android kernel never maps it). A code-like result (STRUCT blocks with ASCII such as "MCUPM"/"tinysys", repeated halfword patterns) would settle it.
2. **The MCU's private TCM or ROM**, not visible to the AP at all. Then the AP can never see the code; the zeroed window plus the INIT flag is all that shows.
3. **DRAM, `mblock-13-MCUPM-reserved` 0x7e900000 / 1 MiB**, loaded by the bootloader. Reading it from XNU is not part of any probe so far (`no-map`, EMI-MPU risk). Only worth asking about if the gap shows nothing.
Nothing here changes what the AP has to do: it never loads the firmware.

### 12.4 Correction to 11.5: the mailbox 3 handshake is not part of DVFS
The `mtk_wait_mbox_init_done` / `mtk_notify_subsys_ap_ready` pair lives in the low-power (cpuidle/MCDI) initialisation (`mtk_lp_plat_wait_depd_condition`, ffffff8008be4e0c): wait for INIT, write ARMPLL/BUCK modes and PWR_CTRL, set AP_READY, wait until `TASK_STA` reads WAIT/INIT_FINISH and 60 s have passed, then register the cpuidle callbacks. Those slots hand MCUSYS, buck and ARMPLL power control to the firmware, which is exactly what must NOT happen under XNU (its idle and CPU power model is not Linux's). The CPU DVFS client (cpufreq probe, IPI id 1) is independent of it in the stock Image, so the DVFS bring-up below never writes mailbox 3 and never sets AP_READY.

### 12.5 Go / no-go
**Stage 2, the ping: GO, subject to its own explicit user approval and a separate image** (not built; I will build it on request). It is the only test that separates "idle firmware" from "dead", its writes are confined to three words of the mailbox-0 send half and one doorbell bit, the same pages were read without a stall in three boots, and the worst outcome is a crashed MCUPM until the next boot with the CPUs unaffected (PWR_CTRL_EN = AP_READY = 0, README section 11.4; CPU clocks unchanged in this boot). Residual risks: the first store into the control page (0x10300154) has never been done, so a bus error is conceivable (unlikely: the page answers reads); and the handler for a 0xdead before PLT_INIT is unspecified (stock never does that).
**Full DVFS bring-up: NO-GO today.** Blockers: (1) liveness unproven; (2) the DVFS command payloads are only partly decoded (cmd 0 table init, cmd 10 init-voltage payload per cluster, cmd 1 initial level, section 2.1: the voltage words and their units are not yet confirmed against the vendor source in `work/nord2-current-kernel` and the PMIC readback); (3) the CSRAM table copy has never been checked against what MCUPM expects; (4) the firmware's behaviour for an unexpected command order is unknown; (5) irreversibility: the init IPIs cannot be undone until the next boot. Each of these has a host-only or read-only way to resolve (below).

### 12.6 Exact safe sequence (every step its own boot, its own approval, abort rules in bold)
**Step 2 - ping.** New boot-arg `n2mcuping=1`, used together with `n2mcu=2` (baseline first). At boot + 60 s, after the read-only snapshot pass: precondition checks (all four control registers 0, `TASK_STA` == 1, window snapshot taken), else print and do nothing. Then, exactly once: store `{0xdead, 0, 0}` to 0x1031fce0, 0x1031fce4, 0x1031fce8 (32-bit, `dsb st`); store 1 to 0x10300154; poll bit 0 of 0x10300078 and bit 0 of 0x10300150 every 50 us for at most 20 ms, printing the time of the first change; if bit 0 of 0x10300078 is set read the 4 words at 0x1031fd30 and store 1 to 0x10300074; no retry, no clearing of a pending doorbell on timeout. Then sample registers, all five mailboxes and the window tail (+0x8000..+0xb800) every 100 ms for 5 s and print every changed word. Never enable SPI 178..182, never write the CSRAM or mailbox 3/4, nothing else.
Outcomes: **A** bit 0 of 0x10300078 set and the reply word non-zero (stock's "Alive"): the firmware services the platform channel. **B** reply bit set, word 0: firmware responds but reports "dead" in the stock sense. **C** 0x10300150 bit 0 was set after the doorbell and cleared again (doorbell consumed) or any window/mailbox word changed, but no reply. **D** nothing changes. D: stop; the firmware is not servicing the AP before AP_READY or is halted, and no further MCUPM step is justified without a new idea (reading the gap with `probe350mcu3` would be the next read-only step). C: stop and think; B: stop. Only A continues.
**Step 3 - platform init (only after A).** Allocate 2 MiB of wired, zeroed, physically contiguous XNU memory that is never freed; write the stock header (`magic 0x504C5401` at +0 and at the last word, `struct plt_ctrl_s` size and `mem_sz`, vendor `mcupm_plt_init`); send IPI 0 `{0x504C5401, phys, 0x200000}` through mailbox 0 as in step 2; expect reply word 1 within 2 s (stock timeout), else stop. After it: re-run the ping once more, then the read-only diff. **Abort on anything but reply == 1.**
**Step 4 - host-only first (DONE, see 12.7):** finish decoding cmd 0 / cmd 10 / cmd 1 payloads and units from the vendor `cpuhvfs`/`mtk_cpufreq` sources and the Image; write the CSRAM-table copy as a pure function checked against the stock level-1 table; extend the host model of CSRAM + MCUPM with the exact acceptance rules; define the fallback "pin min = max = bootloader row for every cluster and send nothing more".
**Step 5 - DVFS init (only after step 3 succeeded and step 4 is reviewed):** copy the verified table into CSRAM `0x11bc10..` (README section 2.2), write min/max to the bootloader rows, send cmd 0, then cmd 10 (x4) with the init voltages read back from the PMIC, then cmd 1 level; after each IPI require its reply; read back `0x354 + 4c`; measure the CPU clocks (`nord2_cpu_mhz`) and compare with the row; **abort at the first reply that is missing, non-zero error, or a clock that moves while the commands say it must not**. No frequency change in this step.
**Step 6 - first frequency steps:** one cluster, one row up from the bootloader row, measure, back; battery-gauge guard as in 0104; then the 0104 ramp logic.
Never in any step: mailbox 3 writes, AP_READY, ARMPLL/BUCK/PWR_CTRL modes, SPI enables.

### 12.7 Host-only decode done (the coordinator's "step 3" = step 4 of 12.6): what the AP actually sends and writes (commands 0, 10, 1), the CSRAM hand-over and the pin fallback
Deliverables, all host-only and not in any image: `cpuhvfs-step3/nord2_cpuhvfs_init.h` (pure functions, 32-bit stores through an ops table), `cpuhvfs-step3/nord2_cpuhvfs_tables.h` (generated), `cpuhvfs-step3/gen_cpuhvfs_tables.py` (reads the vendor table header, reimplements the vendor CSRAM initialisation independently in Python and emits golden hashes; `--check` verifies the committed header against the vendor file), `cpuhvfs-step3/nord2_cpuhvfs_init_test.c` (ASan/UBSan; eight mutations of the header and one of the table each fail it). `run_all.sh` runs the generator check and the test.
Source of everything below: the vendor 4.19 tree on disk, `drivers/misc/mediatek/base/power/cpufreq_v1/src/v2/mtk_cpufreq_hybrid.c` and `mtk_cpufreq_main.c`, `mach/mt6893/*` (the stock Image agrees on the command numbers and the 4-word message).

**The AP-side sequence** (cpuhvfs_pre_module_init at fs_initcall, then the cpufreq probe):
1. DT `mediatek,mt6885-dvfsp`: `state = 1`, `change_flag = 0` (no DOE override of tables or slew rates), `imax_state = 2` (IMAX code is compiled out), reg = CSRAM 0x11bc00 / 0x1400.
2. `init_cpuhvfs_debug_repo`: back up the CSRAM, store the guard words 0x55aa55aa, 0xaa55aa55, 0x55aa55aa, 0xaa55aa55 at +0..+0xc, **zero +0x2a0..+0x1400**, store 0x55aa55aa at +0x2a0, store the PPM limit words `(0 << 16) | 15` (full range) at +0x320 + 4c for c = 0..2 (the vendor loop stops at the CCI cluster).
3. `cpuhvfs_pvt_tbl_create`: zero +0x10..+0x250, then per cluster c (0 LL, 1 L, 2 B, 3 CCI) 36 words at +0x10 + 0x90*c: words 0..15 = `(Vproc_raw & 0xfff) << 16 | MHz`, words 16..31 = `(clk_div << 16) | post_div`, word 32 = 0xffffffff end marker. Then the CCI map: zero 0x1fc bytes at +0xfa0 and store the 32 x 16 byte table (512 bytes) there. The tables are the level's static vendor tables (level 1 = `FY_30G26G` + `CCI_30G26G`, the level of this phone, README section 3). **So the AP does write the OPP tables into the CSRAM**; the firmware does not bring its own. Raw Vproc is the PMIC selector: 160 = 1.000 V, 152 = 950 mV, 104 = 650 mV (6.25 mV steps).
4. **IPI command 0** (`IPI_DVFS_INIT_PTBL`, `cpuhvfs_set_init_ptbl`): `{0, 0, x, x}`: arg0 = segment code 0, the other two words are uninitialised stack in the stock driver (send 0).
5. cpufreq probe: **IPI command 10** (`IPI_INIT_VOLT_SETTING`, `cpuhvfs_set_init_volt`, once per cluster j = 0..3): `{10, j, Vproc, Vsram}` with the CURRENT rail voltages in 10 uV units (regulator microvolts / 10: 100000 = 1.000 V). Rails: LL and CCI use Vproc2 = MT6315 SID 7 VBUCK3 (DA_VOSEL 0x1599) and Vsram2 = MT6359P VSRAM_PROC2 (VOSEL1 0x1eb0 [14:8]); L and B use Vproc1 = MT6315 SID 6 VBUCK1 (0x1499) and Vsram1 = MT6359P VSRAM_PROC1 (0x1e90 [14:8]). Vproc = 300000 uV + (sel - 0x30) * 6250 (sel 0x30..0xbf), Vsram = 500000 uV + sel * 6250 (sel 0..0x6f). Platform clamps for the message: Vproc 600..1120 mV, Vsram 850..1120 mV.
6. **IPI command 1** (`IPI_DVFS_INIT`, `cpuhvfs_set_init_sta`): `{1, cpu_level, x, x}` (level 1 here); then `cpuhvfs_set_sched_dvfs_disable(1)` = store 1 at +0x2bc.
7. Per cluster coming online: store 0x43434f4e ("CCON") at +0x1224 + 4c (`ENABLE_CLUSTER_ONOFF_SRAM`: no IPI command 2).
8. Run time: a frequency request is ONE store of the row index at +0x37c + 4c (`cpuhvfs_set_dvfs`); the firmware reports the current row at +0x354 + 4c; limits are `(limit << 16) | base` at +0x320 + 4c (`cpuhvfs_set_min_max`). Command 4 (`IPI_SET_FREQ`) exists only in the MSSV debug path.
Command numbers (build with `CONFIG_MTK_CPU_MSSV`, as in the stock Image): 0 INIT_PTBL, 1 INIT, 2 CLUSTER_ON_OFF, 3 SET_VOLT, 4 SET_FREQ, 5 GET_VOLT, 6 GET_FREQ, 7 TURBO_MODE, 8 TIME_PROFILE, 9 SES, 10 INIT_VOLT_SETTING. The reply is not interpreted by the stock driver (`ack_data` is never read); completion is the reply doorbell of mailbox 1 (README 11.2).

**Corrections to earlier sections**: (a) sections 2.1 and 8 are confirmed: cmd 0 is `{0, 0}` and the AP does copy the level-1 table into the CSRAM (an intermediate worry that the firmware builds the table itself was wrong); the 4-word message is `{cmd, arg0, arg1, arg2}`. (b) The stock driver never writes voltages, PLLs or rows during init: nothing in steps 1-7 requests a frequency, EXCEPT that the zeroing in step 2 clears the request words (+0x37c..) to 0 = row 0 = the FASTEST row (LL 2000 MHz, L 2600, B 3000 at 1.0..1.05 V) and the default limits allow all 16 rows. In stock Android the cpufreq driver immediately stores its own requests; for a bring-up that must not change frequencies this is a real hazard and is what the pinned plan avoids.

**The pin-to-bootloader-row fallback (defined and tested):** `struct n2dv_plan { level 1; pin; row[3] }`. With `pin` the init plan writes min = max = row for LL, L, B, AND the request words (+0x37c + 4c) with the same rows, and a CCI request from the vendor CCI map (`cci[LL row][B row]`; this CCI choice is an assumption, tested only for self-consistency), so the firmware's first decision keeps every cluster where the bootloader left it. Rows come from the measured clocks with `n2dv_row_for_mhz` (fastest row not above the clock by more than 1 %): LL 1791 MHz -> row 1 (1800 MHz, 950 mV); L 730 MHz -> row 14 (700 MHz, 650 mV); B 730 MHz -> row 15 (659 MHz, 650 mV); CCI 895 MHz row 10 (assumption). Note L and B end up ~4 % and 10 % SLOWER than now (no row between 700 and 902 MHz exists for L, none between 659 and 921 for B), at the table voltage, which is safe. After any failure once an init message has been sent: `n2dv_fallback_pin` (limits and requests to those rows), then stop; nothing is undone and no further message is sent.

**What step 3 leaves open (each has a host or read-only resolution):**
1. The firmware's reply words for cmds 0, 10, 1 are unknown (stock ignores them): step 5 must accept "completion doorbell + any reply" and judge success only by the CSRAM state (`+0x354..` current rows, `+0x32c..` current Vproc written by the firmware) and the measured CPU clocks.
2. The CPU level cannot be read from XNU yet (efuse devinfo word 7, `n2dv_level_from_devinfo` is tested): use the level of the stock analysis (1, devinfo[7] low byte 0x40 from `live.dts`) as a constant and refuse any other.
3. The rail voltages for command 10 must be READ (MT6315 SID 6/7 DA_VOSEL, MT6359P VOSEL1) with the existing `n2pmif`/`n2rail` read path (the GPU work already reads MT6315 SID 7 VBUCK1 0x1499 the same way); that read-only decode step has not been run on the device. If any read fails or a value is outside the clamp, no command 10 is sent.
4. Whether the firmware accepts cmd 0 / 10 / 1 BEFORE the platform init, and whether it needs the mailbox-3 handshake (12.4: not in the stock DVFS path), is unknown until the ping/platform-init steps tell.

**Step 5 revised accordingly:** (1) pre-write the CSRAM with the PINNED plan (never the default plan), verify by reading back the whole table region against `n2dv_pvt_word` and the CCI map; (2) send cmd 0, wait for the doorbell; (3) read the four rails, build and send cmd 10 for j = 0..3 with the clamp checks; (4) send cmd 1 with level 1; (5) `n2dv_sched_disable`, `n2dv_cluster_on` for the clusters; (6) read +0x354.. and measure the clocks: they must still equal the pinned rows (1800 / 700 / 659 MHz within the usual 8 %); any other result: `n2dv_fallback_pin`, stop.

## 13. P18 / patch 0116: the CPU DVFS bring-up in one image (built, not run; needs the user's approval)
Outcome A of the ping (`c6q-bisect-test/mcuping-usb`: doorbell consumed and reply bit set after 0 us, reply word 1 at 0x1031fd30, registers back to 0) shows the firmware services the platform channel. Patch 0116 puts steps 2 to 5 of 12.6 and 12.7 into the kernel behind the boot-arg `n2dvfs`, in the order the user asked for, each step verified and each failure leading to "pin at the bootloader rows, stop". **Boot-arg**: `n2dvfs=1` hand-over only (no frequency change, nothing ramped, placement untouched); `n2dvfs=<MHz >= 500>` hand-over, then the ramp of L and B to <MHz> and the placement switch (not if `n2sch=` is given). It ignores `n2cpu`, `n2mcu`, `n2mcuping`. The thread starts at boot + 60 s.

**Sequence and the line each step prints (`NORD2 DVFS ...`)**
0. Preflight, sends and stores NOTHING: the clocks of LL / L / B must be in the window every earlier boot showed (LL 1700..1900, L and B 650..800 MHz) and give the bootloader rows (LL 1791 -> row 1 = 1800 MHz; L 730 -> row 14 = 700 MHz; B 730 -> row 15 = 659 MHz); all four rails readable and inside the platform clamps (Vproc 600..1120 mV, Vsram 850..1120 mV, Vsram >= Vproc, difference <= 250 mV, the stock probe's own check); the share region accepted (below) and the share buffer mapped, zeroed and the stock header read back. 1. Platform init: `{0x504C5401, 0x70000000, 0x200000}` to mailbox 0, reply word must be exactly 1 within 2 s; anything else: result 6, nothing further.
2. DVFS hand-over: the pinned plan is stored into the CSRAM (guards, zeroed data area, the level-1 PVT table, the CCI map, limits = requests = the bootloader rows; the request window is never written with 0), read back in full (mismatch: result 7, no DVFS message sent), then cmd 0, cmd 10 for the four clusters with freshly read rails, cmd 1 with level 1, the sched-disable word, cluster-on for LL/L/B. 3. Ramp (only with a cap): L and B alternately, one row at a time up to the fastest row not above the cap (cap 2000: L row 4 = 1985 MHz, B row 7 = 1998 MHz), LL stays on its row 1 = 1800 MHz. Each step: gauge readable and below 40.0 C, limits then request stored, the CPU must measure the row within 8 % within 300 ms, else fallback. The CCI request follows the vendor CCI map for the new rows (assumption). Battery guard in the 2 s tick: at or above 43.0 C one row slower per tick (never below the bootloader row), below 38.0 C one row faster per tick until the cap rows, unreadable gauge: hold; if the battery is hot at the start the ramp starts later, from the tick, once it is below 38.0 C.
4. Placement: every tick, `nord2_sched_mode` becomes 0xf when the big cores measure at least 105 % of the A55s (the A78 does about twice the work per clock), back to 0 below 95 %.
**Fallback**: limits and requests of LL/L/B (and the CCI request) written back to the bootloader rows, the engine stops and sends nothing again. It cannot undo the init messages, and a firmware that ignores limits and requests is beyond software.

**The share buffer** (`mcupm_share`, 2 MiB) is NOT XNU-managed memory: the IPI carries a 32-bit address and the kernel's pool is above 4 GiB. It is fixed at physical 0x70000000, free first-bank DRAM: outside every mblock of the live FDT (checked in `n2d_share_ok`, which also refuses anything overlapping the loader, stock kernel, ramdisk and payload window 0x40000000..0x54000000, the Wi-Fi CONN claim and DMA pool, the display framebuffer, the TEE and the MCUPM region), mapped as device memory, written with 32-bit stores only. The firmware is configured without DRAM access (`MCUPM_ACCESS_DRAM_SUPPORT = 0`), so it should never touch it.

**What the approval should know**: first CSRAM stores ever, first DVFS-channel doorbells, first frequency change; L and B end up 4 % / 10 % slower for a moment at the pinned rows before the ramp (see 12.7); the voltage is the firmware's, from the stock table, never the AP's; the unknowns are the firmware's reply words for cmds 0/10/1 (logged, judged only by the clocks), whether it accepts the hand-over without the mailbox-3 handshake, the CCI request rule, and that the battery gauge is the only temperature input (no LVTS).

## 14. Result of the P18 `probe350dvfs` run (c6t) and patch 0117
Log: `gpu/build/hardware-20261025/c6t-test/probe-usb/xnu-live.log`. Preflight clocks passed (LL 1793, L and B 730 MHz: rows 1, 14, 15); LL rails Vproc 1000.00 / Vsram 1000.00 mV passed; cluster L read Vproc 650.00 mV / Vsram 750.00 mV and was REFUSED, result 4 (nothing sent, as designed).
**Cause: my own rule was stricter than the vendor's.** The vendor driver checks the rails the bootloader left in exactly one place, `_mt_cpufreq_pdrv_probe` (`mtk_cpufreq_main.c`): `cur_vsram >= cur_vproc && MAX_DIFF_VSRAM_VPROC >= cur_vsram - cur_vproc` (250 mV). The platform constants I had used as floors, `MIN_VPROC_VOLT 60000` and `MIN_VSRAM_VOLT 85000` (10 uV units), are floors for voltages the AP SETS itself (`MAX(next_vsram, MIN_VSRAM_VOLT)` in the non-hybrid path); the hybrid path never sets a voltage. The reading is the stock pairing: at the 650 mV row the Vsram tracks Vproc + `NORMAL_DIFF_VRSAM_VPROC` (10000 = 100 mV) = 750 mV, below the 850 mV AP floor. Nothing was wrong with the hardware or the rail decode (650.00 / 750.00 mV are the selector values 0x68 and the MT6359P tracking).
**Fix (0117)**: `n2dv_rails_ok()`: Vsram >= Vproc, Vsram - Vproc <= 250 mV, both inside [500 mV, 1120 mV] (the PMIC's own range starts at 500 mV, the lowest table row is 650 mV; the floors only reject a garbage read). Used by the preflight and by the cmd 10 message builder. The preflight now reads and prints ALL FOUR rails before it decides (the P18 log stopped at L and never showed B or CCI); the refusal text names the rule. B shares Vproc1/Vsram1 with L (650 / 750 mV at its row) and CCI shares Vproc2/Vsram2 with LL.
Tests use the exact device readings (LL and CCI 100000/100000, L and B 65000/75000 in 10 uV units): the preflight passes, the four cmd 10 messages carry those values, all four rails are logged, a refusal on L still prints B and CCI; boundaries at exactly 250 mV and one 10 uV step over; the old floors would have refused the device readings (mutation check). `run_all.sh` runs it.

## 15. P19 `probe350dvfs` rebooted the phone (c6u): host analysis and patch 0118 (P20)
Log: `gpu/build/hardware-20261025/c6u-test/probe-usb/xnu-live.log` (5074 lines). What it shows and does not show:
* The only DVFS line is the init line (870). The last line (a `NORD2 GPU JOBS` line) is **cut in the middle** (`seqw=92/`): the stream stopped at an arbitrary instant. The `begin`, clock, rail and later lines do not exist in the log.
* Timeline: the DVFS thread started at about 17.6 s (init line, just before the `t_ms=18588` IOKit line) and sleeps 60 s, so the bring-up began at about 78 s; the log's own clock marks (`t_ms=60757` at the CPUCLK line, 64350 at the Wi-Fi line) followed by ~18 s of the Metal batch (`elapsed_ms=17997`) end at about the same time. So the reset is tied to the start of the bring-up, as reported.
* **The log is host-pulled, not pushed.** The native USB console serves the ring on request (control request 0x54, `nord2-usb-console.py`, host loop sleeps 0.25 s when idle). There is no flush in the kernel: whatever the thread printed in the last 0.25-0.5 s before a hard reset is never fetched. So "no preflight line" does NOT mean "no preflight": the engine may have run its clock lines, the rail reads and even more before the stream was cut.
* **The reset path.** The USB console loop (`nord2_usb_enumerate`, bound to CPU0) is also the only kicker of the MediaTek hardware watchdog (`wdt[2] = 0x1971` every iteration; `wdt_mode 0x7d`, `wdt_length 0xf000` = 30 s, printed by the loader). If CPU0 stops running that loop (for example a panic after a bus error stops the other CPUs), the log stops at once and the SoC resets by the watchdog within 30 s. That matches a silent end of the log and a reboot, and it also means the reset can be up to 30 s after the fault.

**What 0117 changed, and whether it can reset the bus.** The reordering reads the same four registers as P18 (cluster L and B share Vproc1/Vsram1: MT6315 SID 6 VBUCK1 0x1499 and MT6359P VOSEL1 0x1e90; LL and CCI share SID 7 VBUCK3 0x1599 and 0x1eb0). P18 had already read the LL pair and the L pair successfully; P19 repeated them for B and CCI, so there is **no register access in 0117 that P18 had not done**. Eight owner-thread reads instead of four hold the GPU lock for longer (each waits for the owner poll), which delays GPU calls but cannot reset the SoC. The accesses that **only P19 reached** (the rails now passed): (1) `share_init`: first ever `ml_io_map` of 2 MiB (the largest mapping so far) at physical 0x70000000, then 524288 device-memory stores and 4096 reads; (2) the first doorbell on mailbox 0 with a platform init (the ping used the same doorbell and worked); (3) the first CSRAM stores; (4) the DVFS messages. Ranking, with the honest caveat that this cannot be settled on the host: **(1) the share buffer is the most likely culprit** (new address range, large mapping and store count, outside anything proven; a bus error there would panic XNU, stop CPU0's USB loop and end in the watchdog reset), then (3), then (2)/(4); the rail reads are the least likely.

**Patch 0118 (P20), the safe fix**
1. **Only the two rail pairs proven on the device are read** (LL pair, L pair, four PMIC reads, exactly P18's). B and CCI take their partners' values by the stock sharing rule and are printed as "(shared rails with LL/L, not read)". The cmd 10 messages use these preflight values: no PMIC access after the first message.
2. **Announce, then flush, before every hardware access**: a `NORD2 DVFS access N: next is ...` line (rail pair, share buffer, mailbox 0 doorbell, CSRAM plan, every DVFS command, on/off stores, every ramp step with cluster and row) followed by a 400 ms wait, longer than the host's 250 ms pull period. After a hard reset the last line names the access that was about to happen.
3. **Share buffer reduced to what the stock driver does**: only the first and last 16 KiB are mapped; the header (magic, 12, size) and the end mark are stored; no 2 MiB zero fill (the firmware has no DRAM access here, and the stock driver zeroes only the header).
4. **Stage limit `n2dvst=<0..3>`** to bisect a hardware fault without guessing: 0 preflight only (clocks, rails; nothing mapped, sent or stored), 1 + share buffer, 2 + platform init, 3 everything (default; the UI image is full).
Tests (`nord2_dvfs_test`): exactly two rail reads before any message, B/CCI never read even when their model entries fail, stage limits send nothing beyond their stage, every rail read / share call / mailbox event / store group is preceded by a flush (the test catches a missing announce at the share, platform, CSRAM, DVFS command and ramp points, a missing flush, a third rail read, a wrong partner rail, and each stage check).
Images (P20): `probe350dvfs-s0` (preflight only), `-s1` (+ share), `-s2` (+ platform init), `probe350dvfs` (full hand-over, as P19), `ui654fb60dvfs`, and the plain `ui654fb60`. The sensible order on the device is s0, s1, s2, full: each boot adds one new class of access and the last log line names it.
