# Kernel patches 0088-0091 (host-only, not flashed; series continues README-0087.md)

Order: 0085, 0086, 0087 (P1), 0088 (P2), 0089, 0090, 0091 (P3).  Every patch exists as an xnu-series patch
(`NNNN-*.patch`, `-p1`, applies to the stage) and as `candidate-gpu-source-NNNN.patch` (gpu/ + shim/ + tests, apply from `work/`
after the previous candidate patch).  `patched-sources-0088/` and `patched-sources-0091/` hold the resulting files.

## 0088 raise private budget, log rejections (P2)
* `NORD2_GPU_PRIVATE_LIMIT` 64 -> 160 MiB per client (boot-arg `nord2_gpu_priv_mb`, 16..256), device-wide private budget 256 MiB
  (`nord2_gpu_glob_mb`, 16..512), per-context hard limit 384 MiB (= 256 private ceiling + 128 import).  New rate-limited line (1/s):
  `NORD2 GPU BUDGET: <private|global-private|import> rejected pid=.. (name) ctx=.. request=.. KiB private=.. imported=.. all-private=.. limit=.. bos=.. suppressed=..`
  and a configure line `NORD2 GPU: budgets private=.. global-private=.. import=.. ctx-limit=.. ram=.. MiB`.
* RAM headroom: the kernel manages 63,488 pages x 16 KiB = 992 MiB (0x3e000000 window, `vm_page_bootstrap: 60953 free + 2535 wired`). The log has no later
  free-page figure. 160 MiB private is 16% of RAM per client; the 256 MiB global cap (26%) is the real guard. Lower with the boot-arg if userland starves.
  Observed use at the wall: private 65,536 KiB = about six 11 MB (11,075,584 B) full-screen intermediates + 2 MiB heap in backboardd.
  If those textures are never freed the new cap only delays the failure; the BUDGET line (bos, private) will show growth.

## 0089 per-job timing (kernel clocks)
New `NORD2 GPU JOBS:` line, at most once per 2 s while jobs finish (boot-arg `nord2_gpu_stats=0` disables), averages/maxima over the window:
`n fault full win_ms q_us run_us tot_us clean_us inv_us clean_KiB inv_KiB waits gap_us wait_us ret_us seqw=`
* `q_us` submit -> first phase started (includes the pre-job clean); `run_us` start -> completion noticed by the poller (GPU execution + polling interval; there is no GPU
  interrupt, so this is an upper bound with error <= the poll interval, 20 us after 0090); `tot_us` submit -> done.
* `clean_us/inv_us/clean_KiB/inv_KiB`: CPU cache maintenance per job (the 0087 scoped sync), in us and KiB.
* WAIT-side: `gap_us` submit -> WAIT entered (client encode time between submit and wait), `wait_us` time inside WAIT, `ret_us` submit -> WAIT returned (what the client
  sees per job). `seqw=<waits>/<jobs>/<avg us>/<max us>` the same for WAIT_SEQ.
* Reading it: if `run_us` is small and `ret_us` is large the loss is wait latency/encode gap, not the GPU; large `clean_us` -> cache maintenance; large `run_us` -> GPU work (DVFS candidate).

## 0090 low-latency wait + asynchronous submission
Finding: no GPU interrupt handler exists. Completion is detected only by polling `n2c_poll()`: from WAIT (`IOLockUnlock; IOSleep(1); IOLockLock` per iteration), from every submit,
and from a 5 ms timer. A 1 ms `IOSleep` costs 1-2.5 ms on this kernel (timer coalescing + scheduling), which matches the device's ~2.9 ms for even tiny jobs.
* WAIT and the new WAIT_SEQ poll with `IODelay(20 us)` for the first 1.5 ms, `IODelay(100 us)` up to 6 ms, then fall back to 1 ms sleeps (`nord2_gpu_wait_step_us`).
  The gpu lock is dropped around every delay. Expected saving: about 2.4-2.6 ms per small job; 0.5-1 ms per long (8-14 ms) job. Cost: one core busy-polls while a job runs (bounded by 6 ms, then sleeps).
* The tick timer runs at 1 ms (was 5 ms) while any job is unfinished, so a queued chain keeps being started/completed even if the client is busy encoding.
* ABI (for the render owner): `SUBMIT_JM` already returns immediately with the job id. Ids are a per-device monotonic sequence; jobs of one context run strictly in
  submission order, one at a time. New selector `NORD2_GPU_SEL_WAIT_SEQ = 12`: scalars in `{seq, timeout_ms<=5000}`, out `{state, completed_count, first_failed_id}` (3 scalars),
  optional `nord2_gpu_fault_info` struct output for the lowest failing job. It waits until every job of THIS context with id <= seq is terminal, reaps them all, and returns
  4 (all DONE), 5/6/7 (state of the lowest failing job; later jobs still ran) or 2 (timeout: nothing reaped, call again). In-flight window: `NORD2_GPU_MAX_INFLIGHT` = 96 unfinished jobs per client
  (`SUBMIT_JM` returns kIOReturnBusy beyond that; reap with WAIT_SEQ and resubmit); the device job table grew from 32 to 128 records. A client must keep every buffer of a job alive
  (retained by the kernel until the job finishes - release returns BUSY-consumed) and may submit the next job at once; cache maintenance is still done per job at its start/end, in order.
  Old `WAIT(id)` is unchanged and can be mixed. `try_start` is now O(jobs) instead of O(jobs^2) per poll.
* Suggested bridge use: submit every job of a command buffer, remember the last id, one `WAIT_SEQ(last, 5000)`; on state != 4 fall back to the existing broken/fault handling with the returned first_failed_id.
  Expected: removes per-job WAIT syscalls (~2 x 20-50 us each) and lets CPU encoding overlap GPU execution (frame time becomes max(encode, GPU) instead of the sum).

## 0091 selectable cold-start GPU OPP (opt-in; default unchanged = 350 MHz)
* Finding: the log shows `NORD2 GPU CLOCK: ... khz=349900 posdiv=3 normalize=1` and `RAIL target=600000/750000 opp=40`: the boot chain leaves MFGPLL unusable, so the board normalizes it to the
  vendor MINIMUM OPP (index 40 of 41: 350 MHz at 0.600 V VGPU / 0.750 V VSRAM) and nothing ever raises it. `nord2_gpu_clk.h` states "No live DVFS or frequency hopping". The table (n2rail_opp_table) runs to 886 MHz / 0.800 V.
* Boot-arg `nord2_gpu_khz=<kHz>` (exact table entry, e.g. 654000 or 886000; anything else is refused before any PMIC/clock write and the GPU stays on its default only if the arg is absent). Rails are raised to that
  entry's voltage first, then the PLL is programmed with the table's posdiv and Android's DDS formula (all 41 entries verified exact by the host test), MFG domains off, same rollback as before.
  A valid inherited PLL is never retuned (not the case on this device).
* Policy proposal: start with 654000 (OPP 25, 0.650 V) and measure `run_us` in the JOBS line; 886000 only if thermals allow. Live DVFS (raise on UI activity, drop when idle) would need a powered-GPU frequency
  switch (rails up, park mux, retune PLL, un-park) on an idle core; not implemented, not testable offline beyond the register model.
* Expected saving: GPU execution time scales ~1/f for shader-bound work: 350 -> 654 MHz is -46% (blur jobs of 8-14 ms -> about 4.5-7.5 ms); memory-bound work gains less. Small jobs gain almost nothing (they are latency-bound, see 0090).

## Host tests (ASan/UBSan)
core 20 scenarios (new: job timing, async chain/in-order/failure/window, 384 MiB context, scoped cache), transport (WAIT_SEQ validation, wait schedule, budgets), board (cold OPP targets
654/886/370/350 MHz, refusal of non-table OPP, inherited PLL not retuned), rail (all OPPs DDS-exact, VCO range, descending table). Mutation checks: disabling in-order blocking or the in-flight window, or
reverting the clock change, makes the new tests fail.

## Risks
* Nothing here is hardware verified. 0090 busy-polls (CPU) instead of sleeping; the thermal guardian applies to the phone only through the host's own limits, but expect one core busy per running job.
* A WAIT_SEQ client sees later jobs execute after an earlier job faulted (they are not cancelled unless the context faulted at the MMU); inspect `first_failed_id`.
* 0091: a wrong voltage/frequency pairing can hang or damage the GPU domain; the table is the vendor PTPOD-disabled one with the higher of the two segment voltages, but stability at 654/886 MHz on this board
  is untested. The arg is opt-in; first run at 654000 only with explicit approval.
* The job table is larger (128 records); terminal records are only freed by WAIT/WAIT_SEQ, so a client that never reaps can still exhaust it (unchanged behaviour, larger window).
