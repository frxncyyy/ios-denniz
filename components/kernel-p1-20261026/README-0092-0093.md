# Kernel patches 0092-0093 (host-only, not flashed; continues README-0088-0091.md)

Series: ... 0091, **0092** opt-in GPU job interrupt, **0093** stats line with GPU kHz / battery temperature / IRQ counters (P4 images).

## 0092 - GPU job interrupt completion (boot-arg `nord2_gpu_irq=1`, default OFF; polling remains the fallback)

### What the kernel provides (checked in the stage sources)
* `pe_fiq.c` brings up GICv3 with affinity routing (`ARE_NS`, Group 1) and enables only the virtual-timer PPI and the IPI SGI. No SPI is enabled anywhere.
* `sleh_irq()` (SWEET) handles the timer and IPIs itself and forwards every other INTID to the per-CPU `cdp->interrupt_handler(target, refCon, nub, intid)`,
  which is installed with `ml_install_interrupt_handler()` for the CURRENT cpu only (today: IOCPUInterruptController, which has no vector for an SPI).
* The ADT already gives the Mali `interrupts = {362,363,364,365,366}` (GPU, MMU, JOB, EVENT, PWR) with `interrupt-parent = gic` (SPI numbers from the live Android FDT; GIC INTID = SPI + 32 = 396 for JOB).
  Completion has always been polled (no handler registered), which is why `IOSleep(1)` loops were the completion mechanism.

### Why it is wired this way (no change to sleh.c / pe_fiq.c)
Those two objects live in the CI archive, built by Apple clang; replacing exception-path objects with locally compiled ones would put an unproven compiler on every interrupt of the machine.
The driver instead does everything from `Nord2GPU.cpp`:
1. `irqSetup()` (first WAIT/WAIT_SEQ after the GPU is ready): maps GICD from `/arm-io/gic` reg (pe_fiq's own source), then `nord2_gic_spi_configure()` programs INTID 396 as level-triggered, Group 1, priority 0xa0,
   routed to the PE executing the call (preemption disabled), **still disabled**, after checking `GICD_TYPER` range and `ARE_NS` and verifying the priority/route readbacks. It installs `irqDispatch` with
   `ml_install_interrupt_handler` on that PE only.
2. **Learn phase** (state LEARN): the JOB mask is armed while jobs run with the SPI disabled; the SPI is enabled only after `GICD_ISPENDR` shows INTID 396 pending while `JOB_IRQ_RAWSTAT` is non-zero.
   A wrong SPI number, a Group 0/secure interrupt (NS reads of its pending bit are RAZ) or a masked line never confirms; after 8 completed jobs without confirmation the path is FAILED and polling continues.
   Nothing is ever enabled on an unconfirmed INTID.
3. **Active phase**: the waiter clears a flag, arms `JOB_IRQ_MASK`, polls `n2c_poll()` once more, then sleeps on `assert_wait_timeout(&irqFlag, 250 us (1 ms after 2 ms))`.
   Top half (`irqTop`, interrupt context, MMIO + wakeup only): read `JOB_IRQ_STATUS`, write `JOB_IRQ_MASK = 0` (deasserts the level line), count, set the flag, `thread_wakeup`. The bottom half is the unchanged
   `n2c_poll()` in the waiter's thread. Every sleep has a timeout, so a lost/misrouted interrupt costs one slice of latency, never a hang.
4. **Guard**: 64 consecutive interrupts with an empty `JOB_IRQ_STATUS` (a different device on that line / storm) disable the SPI in the GIC and fall back to polling; a log line says so.
* Logs: `NORD2 GPU IRQ: ...` at setup, confirmation, failure or guard trip; the JOBS line (0093) carries `irq=<state>:<tops>/<spurious>/<sleeps>/<timeouts>` (state 0 off, 1 learning, 2 active, 3 failed).
* Boot-args: `nord2_gpu_irq=1` enables, `nord2_gpu_irq_spi=<n>` overrides the SPI number (default 364) for a mapping experiment.

### Expected effect
* Latency: unchanged to within tens of microseconds (poll quantum was already 20 us; an IRQ wakeup is a few to ~20 us). The gain is CPU: no busy-poll core while the GPU runs (up to 100% of one core for the duration of each job, 1-14 ms), i.e. less heat and more headroom for the encoder thread.
* Risk, honestly: this is the first external interrupt this port takes. Hardware-unverified pieces: that INTID 396 is the Mali JOB line, that NS software may configure/enable it (DS=0 firmware), and that routing to the chosen PE works. All three fail safe to polling by construction, but the failure mode of an
  enabled, wrongly-assumed SPI is a spurious interrupt storm, bounded by the guard (64) and the device-side mask. First test: `nord2_gpu_irq=1` on the PROBE image, read the `NORD2 GPU IRQ:` lines.
* If the line cannot be confirmed on the device, the poll overhead is already minimal: 20 us steps for the first 1.5 ms (0090), no lock held while delaying.

### Host tests
`tests/nord2_irq_test.c`: GICD register model: INTID range from `GICD_TYPER`, refusal with affinity routing off (no writes), neighbour priority/group/config bits preserved, level config, route programmed, SPI left disabled and
pending cleared, an enabled SPI is disabled before reprogramming, stuck priority/route readbacks refused with the SPI disabled, MPIDR -> IROUTER mapping (RES1/U/MT bits dropped), the spurious guard (run reset by a real interrupt, trips at 64, stays tripped), sleep slices.

## 0093 - richer stats line
`NORD2 GPU JOBS:` gains `gpu_khz=<PLL kHz read back from MFGPLL CON1>`, `mux=<mfg_sel parent, 1 = MFGPLL>`, `bat_cC=<battery temperature in centi-C>` with `bat_ok=1` only when the fuel gauge value is a real measurement
(SweetBattery `Nord2BatteryTemperatureValid`), and the irq counters above.
**No SoC/GPU temperature is available**: the MT6893 LVTS thermal controller is not driven by this port (needs efuse calibration); the only temperature in the system is the battery gauge (a few degrees behind the SoC and slow).

## DVFS assessment (for 0091's `nord2_gpu_khz`, and design for a live switch)

### Facts from our tables (`n2rail_opp_table`, vendor PTPOD-disabled, higher of the two segment voltages)
| OPP | kHz | VGPU | VSRAM | f*V^2 relative to 350 MHz |
|---|---|---|---|---|
| 40 | 350000 | 0.600 V | 0.750 V | 1.0x (today) |
| 25 | 654000 | 0.650 V | 0.750 V | about 2.2x |
| 0  | 886000 | 0.800 V | 0.800 V | about 4.5x |
Dynamic power scales ~ f*V^2 (leakage rises with V and temperature on top). The log shows the GPU pinned at OPP 40 because the boot chain leaves MFGPLL unusable and the board normalizes to the minimum; nothing raises it.
The kernel has no thermal framework for the GPU and no SoC thermal sensor, so there is no software throttle: whatever OPP is chosen stays until reboot.

### Assessment
* All 41 entries are exact DDS programmings (host test) and use VCO 1.56-3.54 GHz, inside the range the vendor table uses. Voltage ordering (rails first) is the existing, tested `n2rail_on` path; the buck-diff constraint (VSRAM - VGPU in [-0.1, +0.3] V) holds for every entry.
* 654 MHz at 0.65 V is a mid-table point; on this SoC family (Dimensity 1200 class) vendor firmware boosts to 886 MHz only briefly and normally holds the GPU well below that under sustained load because of its thermal policy (assumption from general knowledge of the platform, not measured here).
  886 MHz at 0.80 V with no throttle is a short-benchmark setting, not a UI default.
* **Proposal:** UI image default stays 350 MHz until measured; first opt-in trial `nord2_gpu_khz=654000` on the probe image, then on the UI image. Monitor from the JOBS line: `gpu_khz` (must read 654000 and `mux=1`), `run_us` (expect about -45% on shader-bound jobs),
  `bat_cC` (record at start; abort the run if it rises more than about 4 C above the starting value or reaches ~40 C), `fault`/`full` counts, and absence of `GPU/MMU` faults. Raise to 886000 only for a bounded benchmark with explicit approval.
* If frames are still bound by `ret_us`/`gap_us` rather than `run_us` (the likely case for the many small jobs after 0090), DVFS gives little; decide from the first JOBS lines.

### Live OPP switch (design only; not implemented)
Needs a powered-GPU sequence that today exists only in cold form (`n2rail_on`, `n2clk_mux_on(normalize)` both refuse while powered):
1. Quiesce: block submits (core flag), wait until no slot runs and no job is STOPPING; hold the driver lock.
2. Raising: VSRAM then VGPU to the new point (`n2rail_set_point`, new: same ramp/readback/`BUCK_DIFF` checks as `n2rail_on`, rollback to the old point on failure); then park `mfg_sel` (mainpll_d5_d2), `pll_rate(con1)`, 20 us settle, readback, select MFGPLL, `check_bus_idle` first.
   Lowering: clock first, then rails (never a frequency above what the rail supports).
3. Verify `GPU_ID`/`JS` registers still respond, update `core.hw` shader timings if any depend on the clock, resume submissions.
4. Policy: UI active (job submitted within 200 ms) -> target OPP; idle 500 ms -> 350 MHz; thermal guard: battery temperature above a limit pins to 350 MHz.
Costs: ~150 lines plus a register-world test; the unproven part is the voltage/clock interplay on real silicon, so a boot-time static OPP (0091) should be validated first. Not worth building before the JOBS line shows `run_us` dominating.
