## What was evaluated, and the verdicts

Our panel path (NOTES.md 2026-10-19, `osfmk/arm64/sweet_early.c` in 0082): LK leaves two full-screen 1080x2400 buffers, `0x76e10000` (pitch 4352, read by OVL0_2L/OVL1_2L layer 0, the right half at +2160) and
`0x77806000` (LK's warning layer, OVL0/OVL1 layer 1, pitch 4320, disabled before the polled path starts), all inside the carve-out `0x76e10000..0x78c00000`. The panel is DSI command mode: nothing is scanned
between transfers; a present is `CPU copy (2.6 ms, device) -> MUTEX_EN + DSI_START -> FRAME_DONE (10.3 ms, device)` (`NORD2 FB PRESENT` lines of `hardware-20261025/c6l-test/{ui350,ui60}-usb/xnu-live.log`:
copy 2.3-3.0 ms, xfer 10.35-10.7 ms, avg 12.7-13.3 ms, late_ticks 0).

## 0100 `Nord2GPUUserClient`: SEL_WAIT / SEL_WAIT_SEQ no longer hold the per-connection lock while waiting
Source fact (`Nord2GPU.cpp`, user client `externalMethod`): `IOLockLock(lock); IOLockLock(gpu->lock);` at entry, `IOLockUnlock(gpu->lock); IOLockUnlock(lock)` at `out:`. `waitStep()` drops only the **gpu** lock around `IODelay`/`IOSleep`/the IRQ sleep. So a wait kept the
connection lock for its whole duration (up to 5 s), and every other call on the same connection - notably the next `SUBMIT_JM` - queued behind it. The bridge states the opposite intent
(`n2mb_wait_seq`: "wait for every job with id <= seq WITHOUT holding the bridge lock, so another thread keeps submitting later jobs meanwhile"; one connection `conn` per bridge). The pipeline mode (`tail.queued` /
`TEGU_ASYNC_PIPELINE_DEFAULT`) is **0 by default** (compute_frontend.m:62), so with the shipped defaults the finish thread does not exist and the defect is latent; it bites as soon as the pipeline (A/B word or P2 "scheduled at submit") is enabled, or any process uses two threads on one connection.
Change: after `ensureContext()` the wait copies `ctx`, drops the connection lock (`clientHeld=false`), and re-checks `closed || gpu->stopping` under the gpu lock at the top of every iteration (so the context cannot have been closed and re-used: `closeContext()` sets `closed` first (now an atomic store) and needs the gpu lock for `n2c_ctx_close`).
`out:` unlocks the connection lock only if still held. Lock order stays connection -> gpu; the gpu lock is never held while the connection lock is taken.
Tests (host): `tests-new/nord2_userclient_wait_model_test.c` is a pthread MODEL of exactly this lock protocol, not the kernel code: T1 old protocol delays a second call by 70 ms during an 80 ms wait (defect reproduced), T2 new protocol 0-4 us, T3 close + immediate context-index reuse during a wait never lets the waiter touch the new owner's context (deterministic injection),
T4 mutation without the `closed` re-check DOES touch it (the check is load-bearing); plain and TSan clean. The real file is compiled with the kernel toolchain (`xnu_staged_compile.py`, same flags as the build). **Needs device confirmation** with the pipeline mode on (kernel `NORD2 GPU JOBS` `q_us` of the call after a wait).

## 0101 opt-in scan-address probe `n2scan=<ms>` (off by default)
Proves the only unproven precondition of a CPU-copy-free present on this panel. `sweet_fb_scan.h` (pure, host-tested: address plan, register field rules, test pattern, state machine) and `AppleCLCD::scanBegin/scanPoll/scanStep/scanRestoreRegs`.
After >= 20 presents and >= 8 s of UI, once: checks that OVL0_2L/OVL1_2L layer 0 still show exactly the verified layout (ADDR == panel buffer / +2160, PITCH low 16 bits == 4352, SIZE == 0x0960021c; else the probe is refused and **nothing is written**), maps the slot behind the panel buffer (`0x77806000`, pitch 4608 != 4352 so ADDR **and** PITCH are exercised; 11.06 MB, ends `0x78292000` < `0x78c00000`),
writes a test pattern (striped frame, 8 colour bars, grey ramp), writes ADDR+PITCH of both pipes, **reads them back** (mismatch = restore + log), starts one transfer, holds the pattern `n2scan` ms (1 = 1500, clamp 200..5000), restores ADDR/PITCH, and continues with the pending frame the normal way. Every exit (timeout, driver stop, hold over) restores the base registers; terminal states never retry.
Log lines `NORD2 FB SCAN: ...` (armed / wrote addr ... readback ... / probe frame transferred in N us / restored / finished). The result needs eyes on the panel (photo/video) plus the log: **the register readback proves only that the write stuck, not that the engine used it**.
Known cosmetic edge: a power-off request during the hold fades the old buffer while the pattern stays until the hold ends. Risk when enabled: a wrong layout assumption could show garbage for 1.5 s or leave the panel on the slot until the next present (the restore path writes the base values unconditionally).
Phase 2 (only if the pattern shows correctly): contiguous `< 4 GiB` allocation for panel-geometry surfaces, a CPU-dirty flag from the 0096 tracking to decide the cache clean, ADDR = surface PA + crop offset, PITCH = surface bpr, ownership ends at FRAME_DONE.

## 0102 `SwapWait` semantics, retire-on-GPU, CA frame rate
`sweet_fb_swapwait.h` (pure, host-tested incl. a 400 000-step randomized comparison against a set model for both levels, 11 mutants killed) + `AppleCLCD` integration.
* **IOMFBDisplayRefresh** (NORD2, default on when `fFlushTicks > 1`): property `IOMFBDisplayRefresh = { displayMinRefreshInterval = ticks/60 s * 2^32 }` published before `registerService()`, e.g. 143165577 for 30 Hz. CA's timer then runs at the rate the panel shows; today (`n2fbhz=30`) it renders at 60 fps. Source of the mechanism: reference 0123 on the same iOS 20H392 / ChipID 0x8015 emulation (unverified here: the log line `NORD2 FB: IOMFBDisplayRefresh...` plus a lower `cmd/s`/`gpu` load in the A/B table are the evidence to look for).
* **SwapWait** (`n2swait=<0|1|2>`, alias of `sweetfb_swapwait`, **default 0 = unchanged behaviour**): scalars `[swap id, options, timeout ms]`, options bit 31 = do not block, low bits mode 0/1/2 (see header). Our own earlier note (NOTES.md 10203) recorded the second scalar as "timeout"; the reference decodes it as options. **The first 16 calls' raw scalars are logged at every level** (`NORD2 FB SWAPWAIT: call scalars=...`) so the layout is settled from the first boot, before level 1 is trusted.
  Level 1: a swap is retired when its copy ended or when a newer swap replaced it unseen; not ready -> `kIOReturnBusy` (no-block) or sleeps in 1 ms slices up to the timeout/cap 1000 ms -> `kIOReturnTimeout`. Display off or driver stopped -> always ready. Wakeups at every state change.
  Level 2 (D4, reference 0235): a swap replaced unseen whose surfaces a GPU job still writes (`nord2_gpu_surface_busy`, 0097(c)) keeps its surface references in one of 4 late slots and stays "not retired" until the GPU is done, 200 ms, or the slots are full (forced): CA skips frames instead of queueing them without bound behind a slower GPU. Needed once P2 (CA no longer blocked in `commitAndWait`) ships; today the frontend's blocking commit already limits run-ahead.
  Lock order fLock -> gpu lock (inside `nord2_gpu_surface_busy`); nothing takes them the other way round (the framebuffer holds no gpu-side callbacks).
* New always-on, 5 s rate-limited line next to `NORD2 FB PRESENT`: `NORD2 FB SWAPWAIT: level calls not_ready blocked timeouts swaps_dropped late_held late_forced`.
* Risks: level 1/2 are the first time CA gets "not ready" answers from this driver; a wrong option decoding could make CA skip frames it should draw or block threads up to 1 s per call (capped, `kIOReturnTimeout`). That is why it is opt-in and why the image `ui350sw` (level 2) is separate.

## 0103 P8 defaults and the GPU OPP policy (answer to the ledger K3 / Root's question)
Changes (all in `Nord2GPU.cpp` + `nord2_gpu_transport.h`, host-tested in `nord2_transport_test`):
* cold-start OPP default: **654 MHz when `nord2_metal=1`** (UI images), the 350 MHz minimum otherwise (probe images); `n2mhz=<MHz>` / `nord2_gpu_khz` override both ways (`n2mhz=350` = the old UI default, `n2mhz=886` = opt-in). This also frees command-line characters (the UI base is 585 chars after dropping `nord2wifiemi=0`, limit 607).
* CPU-access tracking default 2 (was 1): it ran in every P6/P7 UI image on the device; `n2trk=1` restores the old default. (Same reason: characters.)
* battery-gauge guard at power-on: above 350 MHz a gauge reading >= 40.0 C (>= 38.0 C above 654 MHz) selects the minimum OPP, logged; an unreadable gauge never blocks (the gauge is probably not up yet when the GPU powers on, so this mostly protects reboot loops). It runs in front of the existing LVTS guard.

**Policy proposal, with what is and is not known.** Known: a 654 MHz cold start runs (c6k: `khz=654000 mux=1`, jobs complete, `bat_cC` 35.3 C over the run). Not known: sustained temperature at 654 or 886 (no GPU/SoC temperature on this port), and any live switch. Dynamic power ~ f V^2 = 350x0.60^2 : 654x0.65^2 : 886x0.80^2 = 126 : 276 : 567 (2.2x and 4.5x). Therefore: 654 is the UI default (with the guard above), 886 stays an explicit supervised opt-in (`ui886`), and *every* run above 350 MHz needs the host side to watch `bat_cC` in the `NORD2 GPU JOBS` stream and stop at a rise of about 6 C over the boot value or 43 C absolute (the gauge lags the SoC by minutes, so these are late alarms, not protection).
**Is LVTS level 2 needed?** For any in-run GPU thermal protection: yes, nothing else gives a GPU temperature, and level 1 (read-only) already proved the controllers are not left running (valid_sensors=0). It is not needed to run 654. Level 2 writes real thermal hardware this port has never touched, with uncalibrated defaults (readings approximate, 10 C margin); the devinfo calibration needs a loader change (`/chosen atag,devinfo` words 116-119, 190-207, design in README-0094). Recommended order: this P8 batch first without it; then one supervised `probe350lvts2` boot (GPU controller only) to see whether readings are sane against `bat_cC`; only then wire `n2lvts_throttle_step` into a live OPP switch. A live switch itself is not built: the GPU powers on once and never again, so it needs the quiesce/rails/PLL sequence of README-0092-0093, which can only be validated on silicon.

## Not done in this round (asked for, with reasons)
* **Present on swap synced to TE (0440 equivalent):** no TE input in this port (the transfer is started and polled), and the reference measured no gain for Metal-style display-link CA; the polled path already gives the vsync grid. Would save on average 8 ms swap-to-panel latency; refactoring the vsync hand-over so the SwapEnd thread can start a present is possible later.
* **Trap path / job state page (#12):** see the table; kernel half is ~80 lines (`getTargetAndTrapForIndex`, shared dispatch) but only pays if the render lead moves `scalar()`/submit to `IOConnectTrap6` and feature-checks via GET_VERSION; measured need is small. Will build the kernel half when the render lead asks.
* **Zero-copy present:** only its precondition test (0101).
