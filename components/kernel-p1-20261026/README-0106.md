# Kernel patch 0106 (host-only, not flashed; P10 images) - why 0104 found nothing, and what was added

## What the P9 device run proves about the MT6893 CPU DVFS
Source: `hardware-20261025/c6o-test/cpu-usb/xnu-live.log` (P9 `ui654fb60cpu`, `n2cpu=2000`), compared with the `n2csram=1` lines of c6m (P8) and c6o `probe-usb`.

1. **The CSRAM address is right, its content is not DVFS data.** The live DT has `dvfsp@0011bc00 { compatible = "mediatek,mt6885-dvfsp"; reg = <0x11bc00 0x1400 ...> }`, exactly what 0099/0104 map (the public MediaTek `cpufreq-hw` bindings use `cpufreq@11bc00` with domain windows at 0x11bc10, +0x120 per domain: for a 1+3+4 part that is CSRAM offsets 0x10, 0x130, 0x250, which the discovery scan covers like every other offset).
2. **The 5120 bytes are SRAM power-up noise.** Over the whole 1280-word dump: 49.7 % of the bits set, 1280 distinct words, no zero and no all-ones word, byte entropy 7.95 bits/byte. And the same words reappear on every boot with only ~3 of 32 bits different (10 words compared on three boots, pairwise mean Hamming distance 2.9 / 3.0 / 3.3; unrelated random words would differ in 16): the signature of an SRAM whose cells power up to their preferred state and which nobody has written since. A running DVFS firmware, a driver that initialised it, zeros or counters would look nothing like that.
   -> **No cpufreq engine is running on this boot chain. 0104's verdict "verified clusters 0x0" is correct, not a bug**, and no choice of domain base can change it. The CPU clocks are whatever the bootloader left (cpu0-3 ~1.79 GHz, cpu4-7 ~730 MHz, unchanged across P8/P9 and across boots).
3. **Why the reference worked and this does not.** On the reference SoCs (MT6789, MT6878) the bootloader loads and starts the DVFS firmware (MCUPM), which fills the CSRAM tables; the AP only writes `ENABLE`/`PERF_STATE`. On this MT6893 the Android *kernel* does that work: the stock 4.19 kernel image (`research/nord2/stock-Image`) contains the strings `[Power/cpufreq] FAILED TO PRE-INIT CPUHVFS`, `[DVFS][CPU_%s][OPP%d] volt:%d, freq:%d` (it computes and prints per-cluster OPP tables, voltages from the CPU EEM/AVS code and efuse), `sspm_ipi success!`, `[SSPM] ...`, `buck vproc1/vproc2`, `vsram_proc1`. A public MediaTek vendor driver for the same family (`sspm-cpufreq.c`, unplugged-kernel, Linux 4.19) shows the shape: probe maps the CSRAM, sends `IPI_DVFS_INIT` to the SSPM co-processor and `IPI_SET_CLUSTER_ON_OFF` per cluster, and a frequency change is `writel_relaxed(opp_index, csram + OFFS_WFI_S(0x37c) + cluster*4)`. Nothing of this has happened under XNU, so the CSRAM was never touched.
4. **What it would take** (not done; none of it is testable without the device and some of it needs approval): reproduce the stock kernel's CPU DVFS bring-up - SSPM mailbox/IPI protocol (`IPI_ID_CPU_DVFS`), the OPP tables with their voltages (per-chip efuse/EEM), the SSPM firmware being present and running (loaded by the bootloader on stock boots; unknown whether it runs here), then the per-cluster index writes. Alternatively the legacy non-hybrid path (ARMPLL + `buck vproc1/vproc2` through the PMIC, as the GPU code does for VGPU) needs register maps this tree does not have. The next concrete step is reading the stock kernel's `cpuhvfs`/`mt_cpufreq` initialisation out of `stock-Image` (disassembly, string cross references) to learn the exact IPI/table protocol, plus a read-only look at the SSPM mailbox registers on one more probe boot.
5. **Placement of backboardd** is still unmeasured (kernel A had no scheduler hooks). Even placed on the big cores, an A78 at 730 MHz is about an A55 at 1.5 GHz (the A55s run at 1.79 GHz), so placement would gain nothing today.

## What 0106 adds (all inert on this chip; this is the preparation for the day a domain verifies)
* **Self-diagnosis line**: `NORD2 CPUFREQ csram is power-up noise: nothing ever wrote it, so no DVFS engine runs (ones 49.7%, ...)` (`n2cf_csram_diagnose`: bits set, zero/all-ones words, equal neighbours). A structured CSRAM would read "structured", a cleared one "empty".
* **Canonical domain probe**: `NORD2 CPUFREQ canonical domain +0x0010/+0x0130/+0x0250: ENABLE .. PERF_STATE .. HW_STATE ..` before the generic scan (the family's fixed bases, raw).
* **Governor decision logic** (port of the reference's 0420: busiest CPU per cluster, 75 % target, up at once, down one row per tick after a 100 ms hold, UI boost floor 2.0 GHz for 100 ms after a kick, clamped between the requested cap and the bootloader row) as pure code with tests, plus `n2cf_goto_row` (verified one-row moves in both directions). **It is not wired into the thread**: its inputs (per-CPU busy time, a UI kick) need scheduler hooks that 0099 does not export, and with no verified domain nothing could run it. Tested only against a model (100 000 random inputs stay inside [cap, bootloader row]).
* **Placement follows the measured advantage**: when `n2cpu >= 500` and no `n2sch=` was given, the thread measures cpu4 and cpu0 every 10 s and sets the 0099 placement mode to 0xf once the big cores measure >= 1.3x the little ones, back to 0 below 1.15x. With the big cores at 730 MHz it never switches on. (Kernel B has the scheduler hooks that act on the mode; kernel A only holds the variable.)
* `n2cpu` command-line cost unchanged (`n2cpu=2000`, 11 characters); placement needs no separate argument any more, which is what lets `n2fbhz=60 n2cpu=2000` fit (606 characters) in both P10 images.

## Images
`ui654fb60cpu2` (kernel A'', `n2fbhz=60 n2cpu=2000`) and `ui654fb60cpuab` (kernel B'', same arguments; the scheduler hooks are in, placement switches on by itself only if the ramp ever makes the big cores faster). On this chip both will print the same diagnosis, the same canonical-domain lines and the same CPUCLK as P9; `ui654fb60cpuab` additionally makes the `NORD2 SCHED` busy/watch lines meaningful (hooks present, mode 0), which answers where backboardd runs.
