# Kernel patches 0097-0098 (host-only, not flashed; P7 images)

Source of the findings: `gpu/build/mesa-darwin-eval-20261026/REPORT.md` section 4. Selector names come from the Topaz kernel patches
(`references/ios-topaz/xnu/patches/0132/0133/0134`), plane layout from `references/mesa-darwin-20261026/mesa-darwin/U2-PROGRESS.md:63-66`.

## 0097 framebuffer: panel rate, present thread, GPU-complete presents

### (a) Panel cap
`sweetfb_hz` defaulted to 10 and no UI boot-arg set it, so at most 10 presents/s reached the panel. New default **30**; `sweetfb_hz=<n>` as before, new short alias **`n2fbhz=<n>`** (command line is 600/607 characters). 0 or >= 60 present on every vsync.
Why 30 and not 60: the panel memory is single-buffered (the DSI engine scans the same 1080x2400 buffer it is copied into), so a present is copy THEN transfer. Estimate from c6k: the console push path measures **14.5 ms** per full transfer
(`fb_ticks`/`pushes` = 27.6 M ticks at 13 MHz / 147 = 14.5 ms), the 10.4 MB WC copy is ~6-10 ms (their measurement: 6 ms for 5.9 MB) -> about 20-25 ms per present, i.e. a ceiling near 40 fps and no room for 60. The new `NORD2 FB PRESENT` line measures it on the
device; `ui350fb60` (`n2fbhz=60`) is the image to try if the measured average is below ~16 ms.

### (b) Present timing
* `vsyncFired` re-arms FIRST, on an absolute grid (`wakeAtTime(prev_deadline + period)`, `sweet_fb_next_tick`): the tick clock (and the vsync notifications CoreAnimation paces itself on) no longer includes copy/transfer time. A handler that runs more than half a period late restarts the grid instead of bursting.
* Presents run on their own work loop thread (`presentFired`): vsync only hands over the newest swap when the presenter is idle (`fPState`); nothing queues behind a copy; a newer swap supersedes a pending one as before.
* The panel transfer is **started and polled**, never spun on: `xferStart()` replicates the register sequence of `nord2_display_refresh()` (clear frame-done, mutex EN0, DSI START 0->1; same constants as `osfmk/arm64/sweet_early.c`), the present thread re-arms a 500 us poll for frame-done (40 ms timeout). The first present (and any present where the link is still busy) uses the
  existing blocking `nord2_display_refresh()`, which also takes the inherited overlay down and proves the link; only after it succeeded is the polled path used. `sweet_early.o` (a CI archive member built by a recipe I cannot reproduce here) is NOT replaced, which is why the transfer registers are driven from the framebuffer driver.
* The copy (~10 MB) still runs on a CPU thread - now the present thread, not the timer. The copy itself is not parallelised or damage-limited (possible next step: copy only changed layers/rows).
* Always-on, rate-limited (one per 5 s, only if something presented): `NORD2 FB PRESENT: n avg_us max_us copy_us=avg/max xfer_us=avg/max legacy timeouts busy_skips busy_forced late_ticks rate_hz`.

### (c) Present only GPU-complete surfaces
`nord2_gpu_surface_busy()` (strong definition in `Nord2GPU.cpp`, weak `false` in `SweetSurface.cpp`): true while a queued/running job declared (via `write_mask`) that it writes an import of that surface. The vsync handler checks the swap's layer surfaces after taking it; if one is busy the swap goes back to the queue (the panel keeps the previous complete frame -
their 0126 semantics), at most 6 ticks (100 ms), then it is presented anyway (`busy_forced`). Today's synchronous per-job waits make surfaces idle at swap time; this matters once submission is asynchronous (WAIT_SEQ). Uses the job table, so it needs no new ABI.

## 0098 IOSurface fixes
### (d) Per-plane bytes-per-row
The plane record (lock result + 0x68 + 0x80 * plane) now carries bytesPerRow at **+0x10** (and +0x08 stays zero) as IOSurface.framework reads it; `IOSurfaceGetBytesPerRowOfPlane` returned 0 for every plane before. Host test: record layout, no write past the 0x80 bytes.

### (e) IOSurfaceAddress / IOSurfaceClientAddress
Creation with a client address no longer ignores it: the creator's range (offset + rows, or the planes' end) is `copyin`-ed into the new surface as a SNAPSHOT (correct for the immutable images CoreAnimation makes this way: icons, layer contents; no longer zeros). An unusable range (zero, larger than the surface, wrapping, unreadable) fails
the creation (`kIOReturnBadArgument`) so the caller falls back. Logged for the first 6 surfaces: `SWEET SURF: <proc> create from client memory ...`. Limitation (documented): later writes by the creator into its own memory are not seen - a true alias (`withAddressRange` + `prepare`, as the Topaz kernel does)
would also need their wrapped-memory plumbing for per-task mappings, kernel mapping and the GPU import (not done; the snapshot is strictly better than zeros and cheaper to validate).

### (f) Unknown selectors
No selector falls through to "success, zeros" by accident any more. `sweet_selector_policy()` gives each an explicit answer (host-tested table):

| sel | meaning (source) | answer |
|---|---|---|
| 0, 4, 13, 34, 35 | create, lookup, limits, lookup/create port | implemented |
| 5 | SetYCbCrMatrix (Topaz 0133) | accepted, no effect (video only) |
| 6, 7 | WrapClientImage / WrapClientMemory (Topaz 0132; not seen in c6k) | **fail, kIOReturnUnsupported**: a zero-filled "success" would hand CoreAnimation a bogus surface, a failure makes it upload the pixels itself (their experience: that works, but CA retries the wrap on every frame, ~11% of CPU samples; selector 6 does not appear in our c6k log, so this only matters if it ever shows up) |
| 9, 11 | SetValue, RemoveValue | accepted, values are not kept |
| 10 | CopyValue | **kIOReturnNotFound** (nothing stored) |
| 12 | BindAccel | accepted, no effect |
| 20 | SetPurgeable | state kept per surface, old state returned (3 = query) |
| 27 | SetBulkAttachments (colour space etc.) | accepted, attachments not stored |
| **40, 41, 43** | **unidentified** (no source names them) | tolerated exactly as before (success, zeroed output) because the UI runs with them; the call shape (scalar/struct counts, arg0) is logged once per selector so they can be named from the next log |
| anything else | unidentified | same as above |

## Expected effects
* Panel rate: 10 -> up to 30 presents/s (the real limit is the 20-25 ms present; verify with the PRESENT line). vsync period steady at 16.7 ms instead of 16.7 ms + present time; no 10-30 ms stalls of the compositor's vsync callbacks.
* CPU: the timer thread no longer burns 14+ ms per present; the present thread polls (copy ~6-10 ms of real work + short wakeups) instead of spinning on frame-done.
* Correctness fixes for plane-based surfaces (YUV, b3a8 plane 1), images created from client memory, and a deliberate failure for the wrap selectors.

## Risks
* The polled transfer duplicates the DSI/mutex register sequence outside `sweet_early.c`; if that file changes the constants must follow (comments mark them). Falls back to the blocking path whenever the link is busy; a 40 ms timeout counts as `timeouts` and the frame is considered shown.
* Two threads can now touch the DSI engine (present thread and the fade-out on the timer thread at power-off); the fade uses the blocking helper which waits for idle first.
* `n2fbhz=60` forces a present attempt every vsync; if a present takes ~25 ms the presenter is simply busy on the next tick (no queueing), so the effective rate is bounded by the present time.
* Snapshot semantics for client-memory surfaces; failing selector 6/7 changes CA's path (intended).
* `SweetFramebuffer.cpo` and `SweetSurface.cpo` are locally compiled replacements of CI archive members (same compiler caveat as before).
* Nothing here has run on hardware.
