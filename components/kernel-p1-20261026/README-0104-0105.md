# Kernel patches 0104-0105 (host-only, not flashed; P9 images)

## 0104 gated CPU DVFS for the big clusters, boot-arg `n2cpu` (off by default)

### What the device data says (hardware-20261025/c6m-test, P8 kernel A)
`NORD2 CPUCLK 0:1791 1:1793 2:1793 3:1791 4:729 5:730 6:730 7:729 MHz big 0xf0` (probe, `ui60` the same within 1 MHz).
* **Proven** (given the 0099 measurement: eight dependent `add #1` per loop iteration against the generic timer): cpu0-3 (A55, rated 2.0 GHz per DT `clock-frequency`) run near 1.8 GHz;
  cpu4-6 (A78, rated 2.6 GHz) and cpu7 (A78, 3.0 GHz) run at about 730 MHz or less (an A78 cannot retire a dependent add chain faster than one add per cycle, so the loop can only
  UNDER-estimate a mis-modelled core, it cannot make a fast core look slow; the A55 cores calibrate the timebase). Two different DVFS domains reading 729-730 is odd and may simply be the same table entry.
* **Not proven**: that anything *caps* the big cores. The simplest reading is "stuck at the bootloader's operating point because nothing under XNU requests a frequency" (the reference device showed
  exactly that on its A76s). The `n2csram=1` words (`cur 2723391134/1249354197/2093223116`, `sched 0x7644da3b/0xf37b02b5/0x716fd871`, `tbl0 0x100d5d8c 0xa26f5b1`) are NOT interpretable as OPP
  indices: either the legacy `cpufreq_v1` offsets 0099 used are wrong for this chip, or the DVFS firmware is not running. The DT has the legacy `mediatek,mt6885-dvfsp` node, not `mediatek,cpufreq-hw`.
* **Placement of backboardd is unmeasured.** All eight `NORD2 SCHED` lines read `big busy 0% ... little busy 0%`: kernel A (0099 level a) has the accounting but not the scheduler hooks
  (`nord2_sched_switch` is called from `sched_prim.c`, level b), so the zeros say nothing. Stock XNU with one pset takes the lowest idle CPU number first (the A55s) by source reading only.
  Even if CoreAnimation ran on an A78 at 730 MHz it would be roughly an A55 at 1.8 GHz, so the 3-4x host/device slowdown is consistent with either placement.

### Design
The module never trusts a fixed offset. `bsd/dev/nord2_cpufreq.h` is pure (host tested, all register access through `struct n2cf_ops`); `bsd/dev/nord2_cpufreq.c` is the kernel glue (CSRAM `0x0011bc00`, 0x1400 bytes via `ml_io_map`, one thread, measurement = 0099's `nord2_cpu_mhz`, gauge = `nord2_battery_temperature_cC` exported from `Nord2GPU.cpp`).
1. **Discover** (60 s after boot): scan every 4-byte offset of the CSRAM for a cpufreq-hw domain block: LUT of >= 8 strictly descending MHz rows in bits [11:0] (100..4000), `ENABLE +0x84 == 1`, `HW_STATE +0x8c` bit 0 (engine running) and no bits above 3, `PERF_STATE +0x88 < rows`.
2. **Verify by measurement**: the top row must fall in one cluster's rating window (ll 1800-2200, l 2300-2800, b 2800-3200) and the measured clock of that cluster's first CPU must be within 8 % of `LUT[PERF_STATE]`. Two independent coincidences with unrelated SRAM contents: fuzzed (120 000 random images: 0 verified; 200 000 single/multi-field corruptions of a valid model: every verified case re-checked field by field).
3. **Ramp** (only `n2cpu >= 500`, only verified clusters `l` and `b`, never `ll`): write `PERF_STATE` one row at a time toward the fastest row at or below the cap (default recommendation 2000 MHz, clamped to the rating 2600/3000), after each write sleep latency+3 ms and require the CPU to measure within 8 % of the row (5 tries, 10 ms apart). A miss writes the original `PERF_STATE` back and freezes the cluster for the boot. An engine that is not already running is never enabled.
4. **Voltage**: the firmware owns Vproc and the PLL; the AP never touches a rail or a PLL. The module only issues requests one row apart, in the order the table lists, and only against an engine that proved itself by the oracle.
5. **Thermal**: the battery gauge is the only input (LVTS is not running; the firmware's thermal SRAM is probably stale under this boot chain): no ramp starts at >= 40.0 C; every 2 s a ramped cluster steps one row slower at >= 43.0 C (never below the bootloader's row), one row faster again below 38.0 C (never above the requested row); an unreadable gauge holds the row and does not block the start (same policy as the GPU OPP guard).
6. **If nothing verifies** (the likely outcome if the firmware is not running or the layout differs) it only logs: `NORD2 CPUFREQ csram +0xNNNN: w0 w1 w2` for the whole region (427 lines), the candidates, and a verdict per candidate. That dump is the data for the next iteration.

Boot-arg `n2cpu`: absent/0 = inert (no thread, no mapping); 1..499 = discovery and dump only; >= 500 = discovery then ramp to that cap. Log lines: `NORD2 CPUFREQ ...`.
Unknowns that remain: the MT6893 may use another request mechanism (legacy `cpuhvfs` with the "sched" word and MCUPM IPI) that this module cannot drive; `ENABLE`/`PERF_STATE`/`HW_STATE` semantics are the MT6789 ones from the reference documentation; the oracle's 8 % tolerance is wider than a single 82 MHz row near the top (3 %), so a one-row error is caught by the cumulative drift over a few rows, not by one step.
Tests: `tests-new/nord2_cpufreq_test.c` (ASan+UBSan): discovery of three domains, one-row steps, caps and clamps, start gate, a firmware that ignores writes (reverted and frozen) or reaches half speed, each refusal verdict, guard hysteresis and bounds, the nine real device words (nothing verifies), 120 000 random SRAM images, 200 000 corrupted models. Real-toolchain compile with the CI flags of `bsd/dev/sweet_touch.c` (`compile_0104.py`).

## 0105 per-context handle limit 256 -> 1024
The render lead saw backboardd fill all 256 handles of its context (215 small client buffers, pooled command blocks, cached code) so that a new code BO failed and the command was dropped.
Two kernel limits stood in the way, and a third lives in the bridge:
* `N2C_MAX_BOS` (256 slots per context) -> 1024. The handle was `(serial << 8) | slot`; the slot field is now `N2C_SLOT_BITS = 10` and the core-wide serial has 22 bits (4 194 303 buffers per boot instead of 16.7 M; at the exhaustion point allocation fails closed with `N2C_E_NO_HANDLE`, it never wraps into a stale handle). A per-slot generation would remove the global exhaustion; not done here.
* `N2VA_MAX_EXTENTS` (256 free VA extents per context) -> 1032. Small buffers are 64 KiB aligned with a guard page, so each live buffer can leave one unusable free gap behind it: with 256 extents the **257th small buffer failed with `N2C_E_VA`** (found by the new host test, unrelated to the handle count). `nord2_gpu_core.c` now `_Static_assert`s `N2VA_MAX_EXTENTS > N2C_MAX_BOS`. This header is also compiled into `nord2_gpu_va.o`, which the build now recompiles from the patched tree instead of the pristine stage.
* **Not changed (render lead's file): `gpu/metal/nord2_metal_bridge.c` `#define MAX_BO 256`** (the bridge's own `bos[MAX_BO]` table and the `code_reclaim`/`cmdpool_reclaim` fallbacks). The kernel limit alone does not stop the command drop until that table is raised to 1024 as well; its comment at line 185 names the kernel cap.
Costs: `struct n2c_core` 103 208 -> ~285 KB (one `IOMallocZero` at start); loops over the handle table (surface lock hooks, cache maintenance scans, reap) are 4x longer in the worst case (about 2 k pointer loads per IOSurface lock with two contexts open).
Tests: `nord2_core_test.c` scenario `test_handle_limit_1024` (22 scenarios): 1024 buffers in two contexts each, the 1025th refused with `NO_HANDLE`, every slot used once, a 32-handle job over the high slots, reuse of a middle slot with a fresh handle and the old one dead, no aliasing across contexts/serials/slots, the serial running out cleanly, close frees everything; mutants (old mask, old shift, old serial limit, extents back to 256) all killed.
