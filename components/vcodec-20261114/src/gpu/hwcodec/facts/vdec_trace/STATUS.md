* 6192 of 21321 register ops on 320x240 (29%) need `VDEC_ALL`; the other windows 2..11 already

* Per AU: ~1040 reads / ~588 writes at the `n2vc_hw` boundary; **~441 distinct read + 430 distinct
  write offsets** per AU (436/425 in a steady state), the same at 320x240 and 1920x1080.  `n2vcu_stats`
  reports 491 reads / 574 writes per AU (it does not see the client's own racing/HW-break batches
  or the OAL's batched read lists); both are in `COST.md` with the reconciliation.
* larb5/larb4 are written at +0x00c only: `0x00000001` request, `0x00010000` release.
* Header decode on the fake: 320x240 `pic=320x240 buf=320x256 dpb=10 MM21 changed=0x23`;
  1920x1080 `pic=1920x1088 dpb=8 MM21 changed=0x23`.  **12/12 and 6/6 AUs displayed**, 0 fake
  register violations, `mmio_bad=0`, `last_bad_mmio_addr=0`.

## 4. Findings reported to other owners

1. **The client's racing restore runs with CORE off (LOCK_LAT).**  DEC01's client powers SOC,
   restores the 68 racing words and only then powers CORE, exactly like
   `mtk_vcodec_dec_clock_on()` (mt6885/mtk_vcodec_dec_pm.c:184-213, which restores in *both*
   branches; the `MTK_VDEC_LAT` branch enables only MT_CG_SOC and MT_CG_VDEC1).  With the kernel's
   conservative map (`VDEC_RACING` -> CORE) that write is refused: 12 EACCES per 12-AU session at
   0x16004100.  The physical domain of the page is [I] (Android has both domains on during a
   decode), so the fix can be on either side: the client takes the CORE reference for its active
   period, or the kernel allows the racing page with SOC only.  Posted to hw-dec01/hw-k02; the
   fake used by run.sh stages the latter (stage.py, skipped once the tree changes).
2. **The larb SLP_CON release word is `0x00010000`, not `0`.**  The vendor reads SLP_CON, writes
   bit 0 to sleep, polls bit 16, then writes the word back with bit 0 cleared and bit 16 still set.
   K02's allow-list ("value & ~1 == 0") refuses that, i.e. 18 writes per session get EACCES.
   Posted to hw-k02/hw-dec07/hw-lead.
3. **The ion share table is a shared 64-slot budget.**  `n2shim_ion_register_share()` returns
   `-ENOMEM` from the 31st share in my first attempt (24 bitstream + 24 frame shares); vpud's own
   buffers use ~34 slots.  With `-ENOMEM` the vendor stops decoding after 3 AUs
   (`ion_import failed`, `no frame buffer`).  The harness now uses 2 bitstream buffers and 12
   two-plane frame buffers.  Posted to hw-dec01/hw-dec05/hw-ip.

## 5. Not done / unresolved

1. **No phone run.**  The page list, the power-state table and the cost figures are host
   measurements; the phone test is the main session's (it has the image and the USB channel).
2. **`RWVC_WIN_VDEC_ALL` is not in the frozen header/V40/T02 yet.**  DEC07 is DONE and DEC04
   validated the text; until it lands, `run.sh` stages the exact one-line V40 entry on a /tmp copy
   (and `n2tr` models the window).  The page list does not depend on it; only the "needs
   VDEC_ALL" counts do.
3. **The fake map for `VDEC_BASE`/`VDEC_RACING` is staged**, not fixed in the tree.  With the
   old map the same 18 pages appear but 12 writes per session are refused; the run would still
   pass its page checks, but `register violations=0` would fail, which is why the stage exists.
4. **Exact per-thread guest instruction count is not measurable today.**  `n2vhost` tracks only
   its own main-thread `icount`; the decode work runs on vpud's service threads and V32's thread
   table has no icount accessor.  `COST.md` reports measured guest CPU time and an `[I]`
   conversion at 35 MIPS, kept out of the counter rows.
5. **Timing rows are not deterministic** (+-10% on this shared host); the determinism checks cover
   the access multiset, `PAGES.md` and the COST counter sections, not the CPU-time rows.
6. **Streams covered:** 320x240 main `-bf 2` (12 AUs), 1920x1080 high `-bf 0` (6 AUs),
   1920x1080 high `-bf 2 -slices 4` (6 AUs, page set identical), a header-only 320x240 stream (the
   probe).  Not yet: HEVC, VP9/AV1, a mid-stream resolution change, >1080p, or a stream longer than
   dpb+2 = 12 AUs (the harness registers 12 frame buffers, the ion budget caps it there; a longer
   stream needs the freed-queue recycling path that DEC01's client exposes but the vendor only
   fills for displayed frames).
7. `probe/vdec_probe.c` keeps an env-gated diagnostic (`N2DEC02_SEED`) that writes words into the
   vendor's instance area.  It was how the `vdec_bs_va` / `bs_fd` layout was identified; the normal
   path does not use it and the test never sets it.
8. The probe's AP side implements only the requests the fake session needs (LOCK/UNLOCK, WAITISR,
   GET/PUT_FB as counters, no racing-word save/restore, no HW-break).  It is a probe, not the
   product client; DEC01 owns that.
9. `dec01_client.c`'s `DC result ... freed=N` is the *freed-queue* pop count; the vendor's own log
   shows all 12 buffers returned to its free list.  `displayed` is the success criterion, `freed`
   is informational.

## 6. Facts for other packages (posted to the board)

* **The vendor's `get_ringbuf` fields are `vsi.dec` fields, not private ones.**
  `libvpud_vcodec.so` `vdec_codec_msg_handler` (0xb6dc), START branch 0xb7a8, calls
  `get_ringbuf` at 0xc56e with `vsi.dec.vdec_bs_va` (0x1ac8/0x1acc) as its ring key; a **zero
  `vdec_bs_va` is the "input handle NULL" failure** (`get_ringbuf` 0x8c76).  `VIDEO_MAX_FRAME = 64`
  in this kernel, so `vsi.dec` is at **0x1a30**, not 0xd30.
* The decode register page set is resolution-independent; the same distinct offsets are programmed
  at 320x240 and 1080p.
* larb SLP_CON: writes at `0x1600d00c` / `0x1602e00c` only; values 0x1 (request) and 0x10000
  (release, ack bit written back), bit 0 request / bit 16 ready.
* GCE is unused for H.264 decode: no `VCU_GCE_SET_CMD_FLUSH` at all in a 12-AU session.
* Power: every vendor register access happens with both VDEC domains on; the only CORE-off access
  is the client's racing restore in the LAT lock.
