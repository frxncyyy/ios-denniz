# Cost of one H.264 access unit on the MT6893 VDEC (host measurement)

Generated by `gpu/hwcodec/facts/vdec_trace/run.sh` (DEC02); do not edit by hand.  Host only.
Two independent counters are reported, because they see different things and the difference is
itself a result:

- **n2tr** sits at the `n2vc_hw` boundary and sees *every* register operation: the vendor's
  guest loads/stores, DEC01's client's own direct ops (the 68-word racing restore/save at
  LOCK/UNLOCK and the HW-break words), and anything batched inside the OAL.  These are the
  counts the page/offset tables use.
- **n2vcu_stats** (`/dev/vcu` model) counts the guest MMIO loads/stores it proxies and every
  GCE flush/command; this is the interface the kernel driver implements, so its `mmio_bad`,
  `last_bad_mmio_addr` and GCE counters are the ones a phone run will show.  It does not see the
  client's direct back-end ops, and the OAL's batched register lists reach the hardware through
  a different entry than a single guest store, so its read count is lower than n2tr's.  The
  reconciliation is printed below and checked by run.sh (writes: n2tr - AP writes == n2vcu).

The guest CPU time is a measurement, not a counter: it varies by about +-10% between runs on
this shared host, which is why the determinism check of run.sh covers the counter sections and
PAGES.md, not the timing rows.  The instruction column is that CPU time x the 35 guest MIPS
figure of `tests/perf/STATUS.md:68` (25-35 MIPS for the interpreter's six-kernel mix) and is
therefore marked [I]; no exact per-thread guest icount is available today (no accessor in V32's
thread table; asked for on the board so a later run can replace this column with a counter).

The 320x240 stream has 12 AUs (main profile, `-bf 2`, so display order is not decode order);
the 1920x1080 stream has 6 AUs (high profile, `-bf 0`).  The per-AU spread is in the raw logs
(`DC START au=...` lines) that run.sh keeps under its output directory.

Reconciliation of the two counters (320x240, whole session):

- n2tr: 19540 register ops (12482 R, 7058 W).
- n2vcu: 12779 (5893 R, 6886 W).  The two counters sit on different paths (the guest MMIO proxy versus the back-end boundary): n2tr also sees the client's own register batches (racing save/restore, HW-break) and the OAL lists, which do not pass through a single guest store.  Page and offset tables use n2tr; `mmio_bad` and the GCE columns are n2vcu's, because those are the numbers a phone run reports.
- window 10 (racing) carries 1225 R + 1020 W over the session.  The client's 68-word restore/save at 0x16004100..0x1600420c is 136 ops per access unit (1632 over 12 AUs); 1776 ops hit those words in total, so the vendor uses them as well.

The number the kernel actually pays per *programming step* is the distinct-offset count, because
the real block answers polls on the first read and the vendor rewrites the same word only when
the value changes:

| stream | AU | n2tr raw R | n2tr raw W | distinct R offsets | distinct W offsets |
|---|---|---|---|---|---|
| 320x240 | 0 (first frame) | 1087 | 593 | 433 | 422 |
| 320x240 | 1 (steady state) | 1103 | 610 | 436 | 425 |
| 1920x1080 | 0 (first frame) | 1087 | 593 | 433 | 422 |
| 1920x1080 | 1 (steady state) | 1103 | 610 | 436 | 425 |

The programming is resolution-independent: the distinct-offset counts of the two streams agree
to within the one-off setup of the first AU; only the values written differ.

## 4. GCE

`n2vcu_stats` counted **0 GCE flushes** and **0 GCE commands** over both sessions.

GCE is not used at all in this decode path: the vendor programs the VDEC blocks with direct
register accesses (the mmap of the windows), and DEC01's client's LOCK/UNLOCK power role is
direct MMIO as well.  The kernel's CMDQ machinery is therefore not needed for H.264 decode on
this SoC; a RWVC_REGS batch per run of adjacent operations is enough.

## 6. What the phone will spend

- Per 320x240 AU: 1628 register accesses (1040 reads, 588 writes), 871 distinct offsets,
  and about 425833 guest instructions [I].
  At the 2-5 us per RWVC_REGS ioctl that VDEC_PROTOCOL.md section 6 assumes, sending every op as its own ioctl would cost 3.3-8.1 ms per AU; batching adjacent ops (DEC04's write-combining, or one list per programming step) is what keeps this path viable at 30 fps.
  The interpreter part is 12 ms at 35 MIPS on this host (a phone A78 should be similar).
- Per 1920x1080 AU: 1464 register accesses (938 reads, 527 writes), 866 distinct offsets,
  about 460833 guest instructions [I].  The count does not grow with resolution: it is the same
  syntax and DPB work; the bitstream bytes and the DDR traffic do grow.
- 64% of the ops are reads (synchronous syntax/status reads), 36% writes.
  DEC04's write-combining can merge the writes only; the reads need a register access each.
