# VDEC pages the vendor stack touches (0x16000000..0x1603ffff, 4 KiB each)

Generated by `gpu/hwcodec/facts/vdec_trace/run.sh` (DEC02); do not edit by hand.  Host only:
the phone's own vpud + libvcodecdrv/libvcodec_utility run under the AArch32 interpreter on T02's
fake hardware, driven by **DEC01's AP client** (`ap/n2ap_vdec.c`: QUERY_CAP, INIT, SET_PARAM,
one DEC_START per access unit, RESET, DEINIT, and the LOCK/UNLOCK/WAITISR/GET_FB/PUT_FB service)
with DEC02's `n2tr` recorder around the back end.  opus-dec1's reference driver
(`dec1/vdec_ref.c`) runs the same two streams once each as an independent cross-check of the
page set.  Nothing here ran on the phone.

Every page below was **seen in the recorder**, i.e. the vendor issued at least one 32-bit read or
write to that 4 KiB page; the R/W column is the number of accesses.  The trace is byte-identical on
a re-run (run.sh checks it twice).  Offsets are from 0x16000000.  `VDEC_ALL` is the one window the
decode path needs (`RWVC_WIN_VDEC_ALL`, DEC04/DEC07 text); run.sh stages that entry into a /tmp copy
of `vcu/n2vcu.c` because the frozen header has not been revised to rev 3 yet.  The recorder itself
models window 12: offsets 0x00000..0x1ffff are powered by VDE (`RWVC_BLK_VDEC_SOC`),
0x20000..0x2ffff by VDE2 (`RWVC_BLK_VDEC_CORE`), and the SMI larb SLP_CON handshake
(larb5 +0x00c, larb4 +0x00c: bit 0 request, bit 16 ready) is answered, as the real larb does.

Inputs: the two n2tr traces of this run (`t320b.trace`, `t1080.trace` in the output
directory; the names in this document are run-independent on purpose, so a re-run produces a
byte-identical file).

### Which power domain each page needs

The `domain` column is the address split the kernel table uses for the decode pages: the VDE
(`RWVC_BLK_VDEC_SOC`) range 0x16000000..0x1601ffff and the VDE2 (`RWVC_BLK_VDEC_CORE`) range
0x16020000..0x1602ffff.  The two clock/register groups live at 0x1600f000 (`vdec_soc_gcon_clk`,
CLK_VDE1_*: MT_CG_SOC/MT_CG_VDEC1) and 0x1602f000 (`vdec_gcon_clk`, CLK_VDE2_*: MT_CG_VDEC0);
see mt6893.dts `vdec@16000000` `clock-names` and `mt6885/mtk_vcodec_dec_pm.c`
`mtk_vcodec_dec_clock_on()`.  Which *MTCMOS domain* each page physically sits in is [I], not
[V]: the vendor never tells the two apart (the Android stack has both on during a decode), so
no host measurement can settle it.  The kernel's conservative rule -- pages below 0x0d and
0x0e are CORE, which takes a hidden reference on SOC (K02 `n2vc_vdec_page_blk()`, DEC07 rev 3)
-- is safe for every access in this document except one, described next.

The `powered while accessed` column is **measured**, not inferred: the recorder logs every
power transition (`P <block> <on|off>`), so classify.py knows which domains were on when each
access happened.  Every vendor access happens with both domains on.  The one exception is the
client's own 68-word racing restore at 0x16004100: DEC01's client answers LOCK_LAT first and
does what `mtk_vcodec_dec_clock_on()` does -- power SOC, restore the words, then power CORE
-- so the restore runs with CORE off.  With the kernel's conservative map (racing = CORE) that
write is refused.  Two ways to make it legal, both consistent with the kernel source: the
client takes the CORE reference for its whole active period (both domains on, like Android),
or the kernel allows the racing page while only SOC is on.  Reported to hw-dec01/hw-k02; the
staged fake used by run.sh models the second (pages below 0x0d as SOC) so the trace is clean.

## 3. Access order: first distinct access per phase and vendor thread

DEC01's client answers the LOCK/UNLOCK/WAITISR requests synchronously on the daemon thread that
issued them -- so the client's own register work (block power, the 68-word racing restore/save)
shares a trace tag with vendor programming.  The interleaving between threads is
scheduling-dependent, but each thread's own program order is not; this table sorts by (phase,
thread, per-thread sequence), i.e. the order each thread touches a new offset, which is what a
kernel or a fake hardware model must be prepared for.  The racing batch
(0x16004100..0x1600420c) is left out here -- it is one memcpy-like block, not programming of the
decode cores -- and is described in section 4.  The page table's `first phase` column is the

The **init** and **header** phases issue 0 and 0 VDEC register accesses: on this path the
vendor parses SPS/PPS in ARM code from the mapped bitstream and programs the blocks only when the
first frame START arrives.  The first register access of a session is therefore in the first
`MARK frame` phase, and a header-only milestone needs no VDEC register window.

SMI larb sleep-protect writes (the one place the vendor writes a page the kernel owns; the
kernel should allow SLP_CON write and nothing else there).  Distinct values, with counts over
both sessions.  Note the **release**: it is not 0 but the whole word read back with bit 0
cleared and the ack bit 16 still set (0x00010000), i.e. the vendor does a read-modify-write.
A kernel rule that only accepts values with `value & ~1 == 0` refuses that half of the
handshake; the measured values below are the ones the rule has to accept:

- 0x0d00c = 0x00000001 (bit 0 = 1), 18 times
- 0x0d00c = 0x00010000 (bit 0 = 0), 18 times
- 0x2e00c = 0x00000001 (bit 0 = 1), 18 times
- 0x2e00c = 0x00010000 (bit 0 = 0), 18 times

## 5. What this means for the kernel

- A single window `RWVC_WIN_VDEC_ALL` = 0x16000000 + 0x30000 (DEC07 rev 3) covers **every** page
  both runs touched; the frozen twelve windows together cover only part of them.  The ten old
  windows stay for K02's own sequences.
- The per-page power rule the kernel landed (pages below 0x0d/0x0e -> CORE, 0x0d and
  0x0f..0x1f -> SOC, 0x20+ -> CORE) is safe for every vendor access measured here, because
  every one of them happens with both domains on.  The only access it would refuse is the
  client's racing restore at LOCK_LAT (12 EACCES per 12-AU session at 0x16004100 when the fake
  modelled racing as CORE).  The fix belongs on one side of that interface: DEC01's client can
  take the CORE reference for its active period, or the kernel can allow 0x16004000 with SOC
  only.  Reported to hw-dec01 and hw-k02; no change to the decode page set either way.
- larb5 (0x1600d000) and larb4 (0x1602e000) are written at +0x00c only (SLP_CON): 0x00000001 to
  request sleep, then 0x00010000 to release (bit 0 cleared, the ack bit 16 written back).
  Read-only would break the vendor's sleep-protect handshake, and a rule that only accepts
  `value & ~1 == 0` breaks the release half.  The allow-list has to accept both words and reject
  every other offset of the two pages.

## 6. Limits of this measurement

- Host fake hardware: no pixels and no real interrupt line (the fake schedules the decode-done
  event and the client's WAITISR service waits for it).  The page set is a property of the
  vendor's register programming, not of the picture, but a stream with more slices, a different
  profile or a mid-stream resolution change could touch more pages; the same run.sh answers that
  with one new vector.  The same page list is produced by both drivers (DEC01's client and
  opus-dec1's reference), which is the cross-check run.sh enforces.
- Accesses are recorded at the `n2vc_hw` boundary.  A page the vendor reads through a *guest*
  pointer (bitstream, MM21 frame) is not a register access and is not listed, by construction.
- The vendor's own `core_index` argument is not visible at the register address; the core column
  is the address region (LAT 0x10000-0x1ffff, CORE 0x20000-0x2ffff, else the SOC/global side).

Header decode result (1920x1080): pic=1920x1088 buf=1920x1088 dpb=8 fourcc=MM21 changed=0x23.
