Bluetooth on the Nord 2 port -- phone test procedure (bt-20261115, pieces 0720-0723, revision bt2). NOT run by the author (host-only agent).

bt2 (after bt18b: q10jfinal18 + bt1 hard-reset ~seconds after n2btd started, no BT0 line): kernel q10jfinal18bt2 + payload bt1/bt1probe
rebuilt. Strict order now: (1) VARIANT=bt1probe (kernel stops after S1 = AP-side register reads only, nothing on conn_infra, nothing
powered); only if it reports "stopped-at-S1" and the phone survives 3 minutes: (2) a stage file 2,3,... by hand or (3) bt1 (full).
After ANY reset/hang: before flashing anything else, from the rescue:
   adb shell 'grep -l N2BT /sys/fs/pstore/dmesg-ramoops-* | xargs cat'     (breadcrumbs, last line = the step that hung)
   (also ENTER=1 gnss-20261114/sweetlog_tail.sh OUT for pmsg/console)
The next boot refuses BT by itself (kernel: "S0 the previous boot reset during the bring-up: REFUSED"; n2btd: "GUARD: ... disabled");
reinstalling payload bt1/bt1probe re-arms it.
bt3 (after the bt2 runs: S1..S7 PASS, then a hard reset 3-6 min after the maxstep 6/7 stops): kernel q10jfinal18bt3, payload n2btd 75d39100.
A stop after S6+ now KEEPS BT powered and hands BGF ownership back to the firmware (kern.n2bt_stop_mode=0; 1 = graceful Linux-order
off: WMT FUNC_CTRL off, fw own, bgfsys_power_off, FW_BT A-die vote bit only); failures after S6 use the graceful off. Then
'quiesce <tag>:' lines (BGF/GPS power + sleep protection, GNSS-polled registers only if GPS up) and 'mon <tag> t=..' host-CSR lines
for kern.n2bt_monitor_s (600 s); state becomes '<state>:settled', and only then N2BT END (kernel guard) / guard file cleared (n2btd).
Ladder to repeat: stage 5, 6, 7 again (each >= 12 min up, read dmesg-ramoops N2BT lines + bt_check), then 8, 9, full.

     NORD2 BT U: BlueTool RunBuiltinScript 'boot' ... -> result 0

  bluetoothd must stop respawning every 10 s (the old "No bluetooth on this device" loop).
  Settings -> Bluetooth: switch ON (green, not grey), "Now discoverable as <name>".

Run 3 -- discovery / pairing / profiles (hands-on, user present; screenshot before every tap)

     under OTHER DEVICES within ~15 s.  Also: the other phone must see "<this iPhone's name>".
  b) Pairing (SSP): tap the device. Headphones: "Just Works", connects. Phone/keyboard: confirm the 6-digit number on BOTH sides

  c) A2DP + AVRCP: with headphones connected, play music (Music/YouTube in Safari). Expect audio in the headphones, play/pause from

     `sysctl kern.n2bt_stats` in a shell) -- tx bytes should grow ~40-45 KB/s (SBC) or ~32 KB/s (AAC); look for "BTIF TX timeout".
  d) HFP: place a call with the headset connected (or Siri / voice memo with BT mic). EXPECTED TO FAIL for audio (see risks):
     signalling may connect, no voice path. Report what Control Center / call UI shows.
  e) BLE: any app scanning for BLE (e.g. a BLE scanner app, Find My is not expected to work) -> devices with RSSI.
     BLE peripheral pairing (e.g. a BLE watch/tag/keyboard) -> GATT read.
  f) Keyboard (HID): pairs (b), but typing is EXPECTED NOT to reach iOS (the kernel has no IOHIDResource/IOHIDUserDevice).

Switches (in a root shell / payload; all run time, the kernel command line is full)
  rm /private/var/db/nord2-bt/enable + reboot     whole feature off (n2btd exits, kernel never touched)
  sysctl kern.n2bt=0                              refuse bring-up (before n2btd runs: e.g. from a boot task)
  echo probe > /private/var/db/nord2-bt/stage     controller only, not shown to iOS; kern.n2bt_publish=1 later publishes live
  sysctl kern.n2bt_quirks=0                       raw controller answers (diagnosis; bluetoothd will likely stall on VSCs)
  sysctl kern.n2bt_trace=500                      log more HCI packets (default first 160)
  sysctl kern.n2bt_adie=0                         stop the A-die top-clock keeper
  sysctl kern.n2bt_force=1                        skip the S1 AP-side checks (only if S1 is wrongly refusing)

Undo

=== bt9 (2026-11-15): kernel q10jfinal29bt (= q10jfinal28bt recipe + bt9 pieces), payload unchanged (n2btd b9132530) ===

Facts behind it [V livecap3 + Linux connac2 driver btmtk_mt66xx.c/btmtk_irq.c/btmtk_btif_main.c, EndCredits/android_kernel_oppo_mt6893]:
  the controller dies ~1 ms .. 4 s after an ACL link comes up (inquiry refuted); first S10q PC 0x1005f2 = the ROM idle loop seen at
  S5 -> the BGF MCU was reset under the running firmware (assert + watchdog [I]); Linux learns about such asserts from BGF2AP_SW_IRQ
  (BGF_SW_IRQ_STATUS 0x18800150 bit25 subsys-reset request) and then power-cycles BT, restoring the RF calibration first.
  Linux steps we skipped: MD coex CCIF (0x10003318 bit0 before BGF power-on), calibration backup after the first func-on and
  restore (+0x5AD02EA5 ready word) before every later one, WMT blank status after func-on. Linux sends NO coexistence vendor
  command on a new connection (kern.n2bt_coex not added: nothing real to send). Vendor event 0xff "04 xx" is passed to the
  Android stack unhandled by the Linux driver (no host answer required).
Changes:
  - guard: the GUARD slot alone decides (END written when the bridge starts; restart = INFLIGHT restart ... END restart);
    run-time hangs never refuse the next boot; a q10jfinal28bt zone that reached "S10e bridge runs" is accepted too.
  - kern.n2bt_keepvote=1: BT wake vote 0x180601a8 held while BT runs, re-asserted every 100 ms (S11w if someone cleared it).
  - kern.n2bt_ccif=1: CCIF BGF_PWR_ON before every BGF power-on (S5c).
  - S7b blank status, S7c calibration saved; S10r restores it before func-on.
  - S11v after every connection/disconnection complete: votes, LPCTL, MCU PC, sleep prot, IRQ.
  - S10q on a hang: BGF sw irq status (SUBSYS/WHOLE-CHIP reset request, DEADFEED) and the firmware assert text (EMI+0x3b000);
    kern.n2bt_diag_bgf=0 skips these BGF/EMI reads (they touch the BGF bus of a dead firmware: NOW slot says "diag-bgf" if that hangs).
  - not done: whole-chip (conninfra) reset - it would take Wi-Fi down and we have no conninfra driver to bring it back.
