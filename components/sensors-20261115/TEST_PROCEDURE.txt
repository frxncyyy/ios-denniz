What it is
  Kernel only (no userland payload needed): q10jfinal25 = q10jfinal24bt (bt6) + 0760
  (device-mmu-q10jfinal25-candidate/ui-sched/nord2-ios-metal-q10jfinal25-ui654fb60dvfs-cap3500-ram5088-sched.img, 15304704 B,
   sha256 66eb02b116ee59d2a50c9bf8c453c3c86ce2c80f31faeb505df578e40f06db56).
  The SCP hub, its firmware start, IPI/mailbox, calibration and the PROXIMITY path are 0284/0531 and are unchanged
  (same ConfigCmd calls in the same order; the proximity HID service and the touch-service proximity are untouched).
  New: four more HID services under SweetHIDButtons' provider, each IOHIDEventService 0xFF00 usage pair:
     ambient-light 0x04, accelerometer 0x03, gyro 0x09, compass 0x0A (transport SPU, Built-In).
  Motion sampling on demand (kern.n2scp_motion=2): the hub samples acc/gyro/mag only while iOS asks (ReportInterval set by
  locationd through the HID event system); a service nobody configured streams while it has a client.
  Light: enabled at 5 Hz (kern.n2scp_lightrate=5120) instead of 0284's on-change request that never produced data.

Flash: kernel q10jfinal25 (image + sha256 in the agent report), same procedure as any kernel-only change. The SCP thread maps at
~90 s and starts the hub ~20 s later as before: sensors work from ~2 min after boot.

1. Logs (USB live log), in order:
     SWEET HID: sensors published mask 0x1f (asked 0x1f, guard 3 opens / 300 s)
     SWEET HID: proximity / ambient-light / accelerometer / gyro / compass sensor registered (0xFF00/0x..)
     SWEET HID: <name> opened (open #1 by IOHIDEventServiceUserClient)            one per service (backboardd)
     NORD2 SCP: step 5: proximity and light (rate 5120) enabled; motion sensors mode 2 ...
     SWEET HID: accelerometer properties set (.. keys): ReportInterval N BatchInterval M     (locationd asking)
     NORD2 SCP: accelerometer 0 Hz -> 50 Hz (mode 2, change 1)  (and gyroscope / magnetometer)
     SWEET HID: accelerometer <x> <y> <z> (IOFixed, 1 clients)
     NORD2 SCP: counts acc .. | to iOS a g m | hz .. light 5120         every 10 s
   BAD signs: "SWEET HID: GUARD: ..." (backboardd restarted 3 times within 300 s after the services appeared: the four new services
   were removed by the kernel itself, proximity kept; send the backboardd crash log + the lines before), backboardd/SpringBoard
   respawning, "light" count staying 0 after 2 min (the light fix did not help: try step 5b).

2. ssh diagnostic (root shell):
     sh n2sensors.sh 20 1        (copy sensors-20261115/phone/n2sensors.sh, or simply: sysctl kern.n2scp_raw)
   Fields: acc raw (mm/s^2, Android convention) and ios_mg (milli-g as handed to iOS); gyr raw (urad/s) / ios_mrad (mrad/s);
   mag raw (10 nT) / ios_muT; lux; prox (1 far, 0 near, -1 none); hz told to the hub; counts per sensor; "to iOS" counts;
   HID part: per service c<clients> ri<ReportInterval us, '?' = never set> o<opens> e<events dispatched>.

3. Orientation / pose test (the gravity vector must follow the pose). With `sysctl kern.n2scp_raw` (or n2sensors.sh) read
   ios_mg for each pose, holding still 2 s:
     a) flat, screen UP on the table           expect ios_mg ~ (0, 0, -1000)
     b) upright portrait (top up)              expect ios_mg ~ (0, -1000, 0)
     c) landscape, left edge down              expect ios_mg ~ (-1000, 0, 0)   (right edge down: +1000)
     d) flat, screen DOWN                      expect ios_mg ~ (0, 0, +1000)
   If an axis has the wrong sign: sysctl -w kern.n2scp_axflip=<bits> (bit0 acc x, bit1 acc y, bit2 acc z; 3-5 gyro; 6-8 compass),
   repeat, and report the value that is right (it becomes the compiled default).
   If magnitudes are ~9.8x off or axes swapped (x<->y), report the raw lines of a)-c).
   Gyro: rotate the phone about its long axis: ios_mrad x/y/z changes sign with the direction, ~0 at rest (< 20 mrad/s).
   Compass: |ios_muT| is uncalibrated (hard-iron of the phone; values ~150-190 uT seen in q10j logs), it must change when the phone
   is turned flat on the table.

4. iOS:
   a) Control Center: Portrait Orientation Lock OFF. Open an app that rotates (Safari, Photos, Calculator for landscape): turn the
      phone to landscape -> the UI rotates within ~1 s; back to portrait -> rotates back. Home screen of iPhone X stays portrait (normal).
   b) Lock on -> no rotation. c) Terraria (landscape game): starts in the landscape side matching the pose, flips 180 deg when
      the phone is turned over.
   d) CoreMotion: Compass app (calibration dance may be asked), Measure > Level (bubble follows the tilt), a game using tilt.
   e) Proximity unchanged: call, phone to the ear -> screen off, away -> on (regression check).
   f) Light: lux in kern.n2scp_raw changes with a hand over the top of the screen / a lamp. Auto-Brightness itself needs MobileGestalt's
      "ambient-light-sensor" answer (cached false on this rootfs): NOT expected to switch on with this kernel alone.

5. Switches (run time, root shell; the boot line is full)
     sysctl -w kern.n2scp_motion=0     motion sampling off (services stay, silent)        1 = always on (0531 old mode)
     sysctl -w kern.n2scp_axflip=N     axis signs (see 3)
     sysctl -w kern.n2scp_lightrate=0  light back to 0284's on-change request; any other value = Hz*1024 (re-sent at once)
  5b sysctl -w kern.n2scp_alslcd=1023  sends OPLUS SET_LCD_INFO (brightness 1023) to the light algorithm once (log "light LCD info")
   Boot time: n2gdv bit 18 (n2gdv=335882 instead of 73738: rebuild with EXTRA_ARGS_OVERRIDE) = none of the four new services.
   Automatic: the kernel GUARD removes the four services after 3 opens within 300 s (backboardd crash loop); reboot re-arms it.
   Fallback image: q10jfinal24bt (same kernel without 0760).

What the q10jfinal25 run showed and what 0761 does:
 (1) no rotation: [V-disasm locationd] on iPhone10,3-class devices locationd's orientation comes from a HID service with usage pair
     0x20/0x8A (HID sensor page "device orientation"), events kIOHIDEventTypeOrientation (10) with DeviceOrientationUsage 0x64..0x6A
     (= UIDeviceOrientation + 0x64) and a first child vendor event (page 0xFF15 usage 2, 8-byte sensor time) - without a newer sensor
     time every update is dropped ("Skipping stale orientation"). Nobody published that service. 0761 publishes it
     ("device-orientation", mask bit 5) and feeds it from a kernel detector on the accelerometer (low-pass, ~250 ms hold, face up/down
     |z| > 0.85 g, landscape/portrait > 0.55 g with 0.15 g margin); current state re-sent every 10 s and when locationd configures the
     service. The accelerometer is kept on while that service is wanted. [I] whether this phone's locationd really takes the AOP path
     (capability bit 6 of its model table) - if it takes the AP path instead, the accelerometer + gyro services (0760) are what it uses.
 (2) gyro "stuck": [I] not a hub fault - the gyro was on only while iOS asked (ReportInterval 5000 / 1000000), then iOS set 0 = off and
     the last sample stays in the diag. -1 now means "not configured" (was read as 1 us). Check with kern.n2scp_motion=1 (step 4).
 (3) magnetometer 0 counts: [I] same: enabled only while iOS asks (Compass app / heading). Check with Compass or kern.n2scp_motion=1.
 (4) light silent: 0761 sends OPLUS SET_LCD_INFO (brightness 1023) 1 s after the light enable and every 20 s up to 6 times while no
     light record came (kern.n2scp_alslcd_auto, 0 = never); logs the hub's IPI_SENSOR replies and any record type it does not route;
     kern.n2scp_lighttype lets you try another ConfigCmd type at run time.

Compass app frozen - findings:
  [V-disasm locationd] CLMagnetometer reads our compass events correctly (type 21, X/Y/Z floats) and iOS does request it (ReportInterval 25000).
  [V-disasm locationd] device motion / heading on this model class comes from the always-on processor: the fusion service is chosen by the
  model capability word (0x1003b5670 bit 4 -> CLSensorFusionService9AxisSPU, bit 3 -> 6AxisSPU, else AP fusion classes), the SPU one parses
  VENDOR-DEFINED HID events with a binary payload (report types 2 = 9-axis with magnetic field/bias, 3 = 6-axis, 4, 0xFF; quaternion +
  rotation rate + magnetic field floats; populateDeviceMotion 0x10017b384), and the compass heading report is part of it
  (CLCompass7::populateMotionType(CMDeviceMotionReport::Compass)). [I, strong] this phone takes the SPU path (it also took the AOP
  orientation path, bit 6, which works now). So: raw magnetometer reaches locationd, but no fused attitude/heading exists -> frozen dial.
  Fix = next piece: a 0xFF00/0x10 "device motion" HID service fed by an in-kernel 9-axis fusion (fixed-point quaternion filter on
  acc+gyro+mag) in Apple's report format (payload layout still to be decoded from 0x1002152fc). Not in 0762.
  n2sens (below) settles it: "deviceMotion (nil)" with mag samples present = the SPU fusion gap; MG/CL lines show availability/authorization.
