# Private pre-panic captured-log drain

The new 0ce01268 failed suffix was not preserved. Its first snapshot ends after MAIN ARM2 while userland continues. That does not establish the eventual radio failure branch or raw state. Earlier b60dd9bc evidence proves that the same apparent ARM2 capture cutoff can be followed by complete DMA initialization, a later stage3 refusal and explicit terminal panic. Do not infer a CPU hang or SW_SYNC value from the new cutoff.

Source facts explain a concrete loss window. Native MTU3 USB is an EP0 PIO service on a separate CPU0-bound kernel thread (`sweet_usb.c:644–652`). Its background loop restores saved DAIF and sleeps1ms between atomic iterations (`539–625`). Wi-Fi main contains no interrupt/preemption disable; its bounded loops do not themselves imply USB thread starvation. Initializer phase2 does write 8,048,640 RX-buffer bytes plus99,072 descriptor bytes to Device memory, with repeated MMIO guards and a barrier per write. That is a concrete long stage with no intermediate progress log, not a measured timing or proven stall. A raw blocked MMIO transaction is not bounded by an outer poll counter.

More decisively, `sweet_early_panic:1046–1070` prints/flushes then immediately enters `nord2_return_to_stock`. The return path masks DAIF/stops other CPUs before input cleanup (`1130–1163`). Retained uncertain radio makes input cleanup refuse and spin before USB cleanup. Therefore an already enumerated USB controller can remain physically present while its CPU0 software service is no longer running; READ54 then times out. The prior preserved panic exhibited exactly the CPU-stop/input-cleanup refusal sequence. This is a source-backed explanation of final capture loss, not proof of the new radio cause.

The minimal proposed change is **before** that panic: after all existing captured MAIN failure diagnostics and shared halt, sleep the failing normal thread to one fixed30-second absolute deadline, allowing the existing CPU0 USB service to drain while all radio resources remain halted/retained. Do not call the USB PIO loop from Wi-Fi: it is private, CPU0-bound, owns global EP0 state, and a second concurrent poller would violate its lifetime. Do not add waits inside the panic path after CPUs have already stopped. No radio read, write, DMA change, retry, cleanup or outer input return occurs during this proposed drain. The original panic still executes immediately afterward.

`failure_drain.inc` uses existing kernel APIs already used by `ni_wait`/`nusb_sleep_ms`: `clock_interval_to_deadline`, `assert_wait_deadline`, and `thread_block`. `preemption_enabled()` is the exact scheduler helper checking both level0 and IRQ enabled (`sched_prim.c:7069–7072`); unsafe contexts print refusal and go directly to panic. A unique private wait channel, one-use latch, unchanged absolute deadline and32-wake bound prevent reentry or early wakeups extending the drain. The proposed owning `wifi_main_bind.inc` adds the helper only inside the existing uncertain-retained-failure panic branch. Clean no-mutation refusal and successful MAIN behavior are unchanged.

This is a bounded drain **opportunity**, not an acknowledgment that the host received every byte. Existing USB protocol has no final-log delivery acknowledgment; the reply decoder increments log_reads when preparing bytes, before EP0 IN completes. A future acknowledged drain would need a separately reviewed USB-side watermark after completed contiguous READ54 transfers. That is unnecessary for this minimal proposal and must not be faked from request counts. A stopped scheduler, wedged bus or absent collector can still defeat delivery; the deadline cannot remedy a prior hard MMIO hang. A live collector must remain active through the new DRAIN marker. No boot/panic radio-cause claim is made.

ASan/UBSan host tests include the actual helper and verify normal fixed-deadline scheduler blocking, one use, IRQ/preemption refusal, bounded early wakeups, failed-wait handling, and loss of sleepable context. No radio or USB callback exists in the helper. Normal CI-derived whole sweet_touch ARM64 compilation passes without forced NORD2. Source/static evidence plus synthetic scheduling tests do not prove device timing or delivery. No active sources, CI, images, gates or device were changed.
