# Implemented transport and CLI extension

The parent-selected protocol supersedes the alternative encoding discussed in REVIEW.md. Operations6/7/8 are GAIN/TONE_TOP/TONE_BOTTOM, with command mask0x1fe. GAIN packs top and bottom absolute-gain STEP INDICES into the low and next nibble of wIndex. Only indices0–6 and zero higher bits are accepted; the shared C helpers provide the single seven-value table and validation. Every other operation requires index0. The existing request generation field carries and echoes this argument, preserving duplicate-token identity.

Version1,64-byte capabilities and192-byte replies remain unchanged. Status fields42–47 are gain_top, gain_bottom, gain_max, ramp_frames, dma_peak_top and dma_peak_bottom. Legacy field indices remain unchanged. New CLI accepts mask0x3e or0x1fe, queries each operation's supported bit before writing, and verifies both opcode and argument in the reply. Old kernels omit the new JSON fields rather than falsely reporting zero gain. A preexisting old CLI still rejects a new kernel's expanded command mask; this change supplies the updated compatible client.

Examples: `gain --top 256 --bottom 512`, `tone-top`, `tone-bottom`. Both gain values are mandatory exact integers from the seven-step set. The CLI retains its single mutation write even if the ACK is lost. It does not add raw register, arbitrary memory, PCM or amplifier controls.

Only the five assigned transport/CLI/test files were edited. Strict C11 warnings with ASan/UBSan pass, including all65536 argument encodings,49 valid pairs, USB setup framing, changed-argument replay, generation mismatch, new tones, token limit and append-only fields. Eleven Python tests against the real C transport pass, covering old/new capability masks, unsupported mutations, parser validation, all gain pairs, ACK loss and stale/reboot replies. The C test statically checks that protocol and current hardware ceilings both equal1024. Exact file hashes and test evidence are in implementation-receipt.json.
